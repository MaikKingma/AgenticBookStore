# Spec 03 Inventory: Shaping Notes

Source of truth: `docs/spec-pack/specs/03-inventory.md`. These notes restate it, record the engineering decisions the spec leaves open, and map every scenario to a test. Shaped autonomously by the orchestrator agent on 2026-11-07 with two research agents, one senior research agent, one tech-lead strategist and the QA lead.

## Scope

In scope (the pack spec's "What changes"): the `StockItem` aggregate with `Quantity`, the `DomainEvent` marker interface, `StockRunningLowEvent` and `InsufficientStockException` (plus five further domain exceptions the behaviour list implies); `InventoryFlow`, the `StockItemDataService` port, `StockItemDTO`, `StockItemDomainMapper`; `CatalogueFlow.addBook` opening an empty stock item in the same transaction; the command adapter (receive stock, correct stock after a stocktake), the query adapter (stock for a book, books at or below the reorder level); `BookView` and `BookDetailView` gaining `available` and `inStock`; the data adapter with `V2__create_inventory.sql`; `InventoryIntegrationTest` with the after-commit and rollback scenarios; the `CatalogueIntegrationTest` update; `http/inventory.http`.

Out of scope: restock ordering at the distributor (specs 06 and 07), the production `process` listener (spec 07), releasing reservations (Level 3), multiple warehouses, HTTP endpoints for `reserve` and `ship` (spec 04 calls them from `OrderFlow`), mapping a stale update to 409, a batch stock lookup for the search view, ArchUnit changes.

## Decisions

Binding decisions from the main session (recorded in `docs/spec-pack/orchestrator/progress.md`) and the orchestrator's choices on the open questions of research and strategy. The letters match `plan.md`.

- B1 `StockRunningLowEvent.occurredAt` needs the time, so `StockItem.openFor(BookId, Clock)` and `StockItem.restore(..., Clock)` take the `Clock` (the `ddd-building-blocks` skill names this case); `receive`, `reserve`, `ship`, `correct` keep the spec signatures. Unlike `Book`, `StockItem` keeps the `Clock` as a field because `reserve` and `correct` stamp events later. The flows inject the spec 02 `Clock` bean (`ClockConfig`); no second bean; `domain` depends on `java..` only.
- B2 One flow coordinates two aggregates: `CatalogueFlow.addBook` saves the book (a `saveAndFlush`, so the row exists before the foreign key row), then opens the stock item through the `StockItemDataService` port in the same transaction; it never calls `InventoryFlow`. `CatalogueFlow` takes no `ApplicationEventPublisher`: the spec raises events after `reserve` and `correct` only, so `openFor` registers none and there is nothing to publish; `StockItemTest.openForRegistersNoEvent` guards the assumption, and a later spec that makes `openFor` raise an event must revisit `CatalogueFlow`.
- B3 `GET /inventory` supports only the documented form `?lowStock=true`: the parameter is required and must be the literal, case-sensitive string `true`; anything else (missing, empty, `false`, `TRUE`, `1`, `maybe`, a repeated parameter) is 400 `validation-failed` with `details = [{field: "lowStock", message: "must be true"}]`. Implemented as `@RequestParam(required = false) String lowStock`, one controller check, one nested exception `InventoryQueries.InvalidQueryParameterException`, one new `QueryExceptionHandler` method; no constraint annotation on a controller parameter (tech stack: Jakarta Validation on `*Payload` records only), no `MissingServletRequestParameterException` handler. `InventoryFlow` has exactly `receive`, `correct`, `findByBookId`, `findLowStock`.
- B4 `BookDetailView` stays a superset of `BookView`, so both gain `available` (int) and `inStock` (`available > 0`) as their last components. `BookQueries` composes `CatalogueFlow` and `InventoryFlow` (the query adapter composes; the flows stay independent): `search` asks `InventoryFlow.findByBookId` per book in result order (up to 100 calls per search, accepted for this workshop app; a batch lookup is a follow-up if a later spec needs it); `get` asks the catalogue first so an unknown book is a 404 before any stock call; a missing stock item is an invariant violation whose 404 propagates.
- B5 Error contract: 409 `on-hand-below-reserved` (title "On hand below reserved", empty `details`, mirroring `book-discontinued`) from `OnHandBelowReservedException`; 404 `book-not-found` from the nested port exception `StockItemDataService.StockItemNotFoundException` (a stock item exists for every book, so the missing item means an unknown book). Bean validation gives the spec's 400 for an invalid quantity: `ReceiveStockPayload(@NotNull @Min(1) @Max(1000) Integer quantity)`, `CorrectStockPayload(@NotNull @Min(0) @Max(10000) Integer onHand, @NotBlank @Size(min = 3, max = 200) String reason)`; the fields are `Integer`, because Jackson 3 rejects a missing primitive with a 400 that carries no `validation-failed` body. The domain enforces the same bounds (`ReceivedQuantityOutOfRangeException`, `InvalidQuantityException`, `InvalidStocktakeReasonException`), translated by the flow to 422 `quantity-out-of-range` and `invalid-reason`; unreachable over HTTP and tested at domain and flow level. The domain reason rule is "not null, length 3 to 200" with no `strip()` and no blank check, so it accepts everything `@NotBlank @Size` accepts (`@NotBlank` uses `String.isBlank()`, so any `Character.isWhitespace` character counts as blank and the payload is stricter than the domain; corrected at finalize, A3).
- B6 The test after-commit listener is `StockEventRecorder` in the test root package: a plain class without stereotype annotation (a test-sources `@Component` would be component-scanned and the import ignored), registered once through the existing `@Import` on `IntegrationTestBase`, autowired there and reset in the existing `@BeforeEach`, so every integration test keeps sharing one Spring context. It records `AFTER_COMMIT` and `AFTER_ROLLBACK` deliveries and holds a `BEFORE_COMMIT` listener that throws while a toggle is set: the rollback scenario sets the toggle, corrects stock down to the reorder level, gets a 500, and proves the stock row rolled back, no `AFTER_COMMIT` delivery and exactly one `AFTER_ROLLBACK` delivery (the non-vacuity proof that the event was published). A plain `@EventListener` thrower was rejected: without `@Order` it stops the transactional listeners from registering, so "no delivery" would be vacuous; failing the port was rejected because the save fails before the publish. `IntegrationTestBase` also carries `@MockitoSpyBean StockItemDataService` so one test can make the stock save fail and prove `addBook` rolls back the book row too (the only behavioural proof of the two-aggregate transaction; Spring resets the spy after each test).
- B7 `DomainEvent` is a marker interface in `domain`; `StockRunningLowEvent` is a record with JDK-typed components implementing it. `process` is untouched (spec 07 adds the listener); the existing ArchUnit exception for `process` to `*Event` stays; no rule changes (21 rules, 40 self-tests). "Publishing happens in flows" is not enforced by a rule; the plan gates it with a grep.
- B8 `V2__create_inventory.sql` creates `stock_item` with `book_id uuid` primary key and foreign key to `book (id)`, `on_hand`, `reserved`, `reorder_level`, `reorder_quantity` as `integer`, `low_stock_signalled boolean`, `version bigint`, all `not null`, constraints `pk_stock_item` and `fk_stock_item_book`, no `check` constraints (V1 style; the domain enforces the rules; `validate` ignores them). `StockItemJPA` has an assigned `@Id UUID bookId`, primitive `int` fields, `boolean lowStockSignalled`, `@Version Long version` (boxed, so a new entity inserts without a merge), no relationship to `BookJPA`. `StockItemJPAMapper` is a static utility like `BookJPAMapper`. `StockItemDataServiceImpl.save` finds by id and copies into the managed entity or inserts, with `saveAndFlush`; the foreign-key violation is not translated.
- B9 `findLowStock` returns the items whose available stock is at or below the reorder level, ordered by available ascending (most urgent first), then book id. The spec is silent on the order; this one lets the integration test pin the order by availability independent of random UUIDs. Trap: `UUID.compareTo` is signed and PostgreSQL orders `uuid` unsigned, so the slice test pins the tie with fixed UUIDs whose first hex digit is 0 to 7 and never uses `isSorted()`.
- B10 Stored `onHand` has no upper bound (the spec is silent; `receive` keeps adding, `correct` is bounded by `Quantity` at 10000); reserved, reorder level and reorder quantity are never negative; `onHand >= reserved` is an invariant of both factories.
- B11 Non-ASCII: the editing tools decode a typed backslash-u escape into the character itself. T5 replaces the six literal U+2003 characters of `CatalogueFlowTest.java:399` (spec 02 follow-up F22) with a constant built from the code point, `Character.toString(0x2003)`; every Java file spec 03 writes is checked byte-level. `IsbnTest.java:67` and `:74` keep their deliberate Arabic-Indic digits (untouched file; follow-up).
- Order of checks (L17 of the strategy): both commands load the stock item first (an unknown book is a 404 even with an invalid quantity, as `changePrice` does); in `correct` the domain checks the reason before the reserved stock; pinned at flow and domain level.
- Accepted defaults carried from spec 02: a stale stock update is an unmapped 500; malformed JSON and a non-UUID path give Boot's default 400; Jackson coerces `"5"` to 5 and truncates `1.5` to 1 for `Integer` fields.
- Contradiction check (strategy section 1.1): thirteen findings, none a stop. The spec's "Invalid quantity ... 400" and the standard's 422 for domain rules are consistent because bean validation runs first; the spec's "every flow that changes a stock item publishes" is satisfied by B2 because `openFor` registers nothing; the standard's "`process` listeners run only after a successful commit" is what the test listener proves.
