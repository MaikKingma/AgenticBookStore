### Spring events, the test listener and the lowStock parameter (res-2, senior, verified in a scratch Boot 4.1.2 project on PostgreSQL 18.6; Spring 7.0.10, Jackson 3.1.7, Hibernate Validator 9.1.5)

A plain record published with `ApplicationEventPublisher.publishEvent(Object)` inside the `@Transactional` flow reaches a `@TransactionalEventListener(phase = AFTER_COMMIT)` typed on the record, synchronously on the caller's thread after the commit and before the HTTP response; outside a transaction it is silently skipped (`fallbackExecution` false). An `@Import` on the abstract base class is honoured and keeps one shared context; a test-sources `@Component` would be component-scanned instead. Rollback device: a `BEFORE_COMMIT` listener that throws while a toggle is set rolls the transaction back (the stock row keeps its old value), `AFTER_COMMIT` stays silent, `AFTER_ROLLBACK` fires once, and the caller sees a 500 with Boot's default JSON body; the exception is not wrapped. Rejected devices: a plain `@EventListener` thrower without `@Order` aborts the multicaster loop before the transactional adapters register (a vacuous "no delivery"); a failing port fails before the publish. An exception inside an `AFTER_COMMIT` listener is logged at ERROR and swallowed, so tests assert in the test thread. Jackson 3 does not bind a missing `int` to 0: the request fails with a 400 that carries no `validation-failed` body, so payload fields are `Integer` with `@NotNull`. Class-level `@Validated` yields `ConstraintViolationException`, not `HandlerMethodValidationException`, and constraints on controller parameters break the tech-stack rule. `boolean` binding accepts `TRUE`, `1` and `yes`; `params = "lowStock=true"` on the mapping gives an empty 400 from outside the advice. A `@RequestParam(required = false) String` with one controller check gives one `ProblemDetail` shape for every bad form. `InOrder(port, publisher)` detects a reversed save and publish; the `@WebMvcTest` slice never builds the flow.

### The stock_item data adapter (res-3, probed in the module; Hibernate 7.4.13)

The V2 DDL validates under `ddl-auto=validate` with an entity holding an assigned `UUID` id, primitive `int` fields, `boolean` and `Long` `@Version`; a null version on a new entity gives a plain insert (`Long`, never `long`). Insert versus update mirrors spec 02: `findById`, copy into the managed entity or insert, `saveAndFlush` (select then insert for a new row, select then `update ... where book_id=? and version=?` for a change). JPQL `where s.onHand - s.reserved <= s.reorderLevel` includes equality. A stock item for an unknown book fails with `DataIntegrityViolationException` whose cause names `fk_stock_item_book`. A stale write throws `ObjectOptimisticLockingFailureException`. The book row is seeded with a `JdbcTemplate` insert (or `persistAndFlush(new BookJPA(...))` from the same package). A second `@DataJpaTest` class with its own `@Import` set starts its own context and reuses the one static container (verified: one container, two `Started` lines). `DatabaseCleaner` covers `stock_item`. Trap: `UUID.compareTo` is signed while PostgreSQL orders `uuid` as unsigned bytes, so ordering assertions use fixed UUIDs whose first hex digit is 0 to 7 (or compare `toString`), never `isSorted()`.

Approach A: inside out per layer, test first, with the bean-order flip (the data adapter merges before the flows because a `@Service` without its port bean breaks every full-context test; `CatalogueFlow` gains the stock port before `BookQueries` composes stock, so every book the integration tests add has a stock item; the book-view change and the `CatalogueIntegrationTest` pins merge together).
