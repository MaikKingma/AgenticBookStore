# References: Spec 07 Restock process adapter

## Research summary (2026-11-09)

- Bookstore anchors: no restock state exists yet; the latest migration is `V3__create_orders.sql`. The port `DistributorAppService.requestRestock(String isbn, int quantity, String retailerReference)` (spec 06) returns `RestockConfirmationDTO(restockOrderId, quantity, expectedDeliveryDate, backordered)` and has three nested exceptions that `CommandExceptionHandler` already maps to 404, 422 and 503. `process` holds only `package-info.java`. ArchUnit rule 9 is already a named `ignoreDependency` in `ArchitectureTest` (22 rules) and the `LeakyDelegate` fixture already shows `process` may not use a non-event domain class. Blast radius in tests: `StockItem.restore` (about 50 call sites), `new StockItemDTO(` (113 test call sites), the 6-key `StockView` pinned in `InventoryQueriesTest`, `InventoryIntegrationTest`, `OrderIntegrationTest` and `DistributorImportIntegrationTest`. The `IntegrationTestBase` distributor mock has no default answer. Baseline on factory 824af83: bookstore 931 tests, distributor 190, referee 17.48 s.
- Transaction semantics on Spring Framework 7.0.10 / Boot 4.1.2 (verified in source and with a PostgreSQL probe): the `AFTER_COMMIT` listener runs synchronously on the request thread before the response is written; any exception escaping the listener is caught by `TransactionSynchronizationUtils` and logged at ERROR, so the triggering order stays committed and its response unchanged; `REQUIRES_NEW` opens a real new transaction on a second pooled connection while the outer one is still held (Hikari default pool 10); a rolled-back transaction never fires the listener; an exception that crosses a joined transactional proxy marks the transaction rollback-only even when caught, so the catch for the signal reset must sit inside the flow around the non-proxied port; a class-level `@Transactional` on the listener class fails startup unless it is `REQUIRES_NEW` or `NOT_SUPPORTED`; an order that fails with 409 publishes no event; `OutputCaptureExtension` (already used in the repo) captures the WARN lines; `@MockitoBean` resets after every test, so the default answer is stubbed in a base `@BeforeEach`.
