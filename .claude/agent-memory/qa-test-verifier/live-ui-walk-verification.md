Rule: reproduce a recorded walk with your own data and scripts, seeded to the same figures, and compare value by value; never cite the implementer's JSON.
**Why:** seeding the same books, prices and stock through the REST commands makes every money string, 409 body and order total byte-comparable, while ids and times differ by design.
**How to apply:**
- One control script with subcommands (`docker-state`, `ports`, `pg-start`, `jar-start`, `jar-stop`, `pg-stop`) writes a dated SP file per call; take `docker-state`/`ports` before and after; use a different throwaway port. A fresh throwaway DB has no books: seed via `POST /books/commands/add` (202 with id, hyphenated genres like `science-fiction`, valid ISBN-13 check digits).
- playwright-cli: one `async page => {...}` file per phase via `run-code --filename`, `--raw` redirected to SP; attach `console`/`pageerror`/`response`/`request` listeners inside, `off` them in `finally`. Fill number inputs with `locator.fill` (fires `onChange`); a `window.__marker` proves "no reload". `URL` is not defined inside `run-code`: take the origin from `page.url().split('/shop/')[0]`.
- Library walk instead of the daemon: a node `.cjs` can `require` the `playwright` package under the global `@playwright/cli/node_modules/` and launch chromium itself (a `newContext({viewport})` per phase and size, `CHECK PASS|FAIL` lines, exit code = fails; run from a script that `cd`s to a scratch dir). End every walk with a control context calling `console.warn('<tag>')` and assert exactly one hit: zero console messages is otherwise indistinguishable from a detached listener.
- Negative control for a fix: `git archive <pr-base>` into scratch, `./mvnw -DskipTests package` (8 s with Node cached), run that jar on a second port against the SAME throwaway DB (`--server.port=8081`), drive both builds with one script, one new `-s=` session per build.
- Dev-mode console check (the jar serves a production React build with warnings stripped): the Vite proxy target is fixed at 127.0.0.1:8080, so start a SECOND tip jar on 8080 against the same DB and Vite from the `git archive` extraction (`--port <free> --strictPort`); derive the dev journey from the jar journey by string replace and switch to books that still have stock. Dev consoles show only `debug`/`info` lines (`[vite] connecting`, React DevTools hint): count `error`/`warning` types. WITHOUT a backend: Vite alone, `/books` and `/inventory` mocked with `page.route` in `run-code`; an uncaught exception in a route handler (`new URL` undefined there) kills the playwright daemon with a bare "Session closed": parse the href by hand, try/catch around `route.fulfill`, `unrouteAll` in `finally`. The catalogue remembers its last search in sessionStorage: clear it before a second listing visit; select cards with `li:has(article)`.
- Background children started inside `with-budget.sh` keep running after it exits (Vite stayed on its port): pid files plus a `stop` subcommand and an `lsof -tiTCP:<port>` sweep.
- A walk provoking a 4xx on purpose (insufficient stock 409) logs Chromium's `error: Failed to load resource: the server responded with a status of 409 (Conflict)` with the API URL as location, in jar and dev mode: it is the browser's network log, not an app or React diagnostic: quote it, attribute it by location URL plus an empty `console.` grep over production `src`, let the lead judge.
