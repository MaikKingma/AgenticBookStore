Rule: in a combined-criteria search scenario, every criterion needs a data row that only THAT criterion excludes. Probe each criterion one at a time, dropping it at the adapter (pass `null`).

**Why:** spec-pack scenario data is often redundant. In "author=austen&genre=FICTION", every fiction book was by Austen, so dropping `author` left the exact list green, while the plan's extra row (an Austen book in another genre) only made genre load-bearing. The slice test killed the drop, but the full-context scenario did not.
**How to apply:**
- For each filter, ask which row would appear if that filter were gone. If no row would appear, the filter is a survivor. Prove it with a temporary witness class extending `IntegrationTestBase`: the same context, so no extra Started line. Show it passes on the real code and fails on the mutant, then `rm` it.
- View probes: check which endpoint the asserting test reads. `GET /books/{id}` serialises the detail view, `GET /books` the list view. A price-format probe on the list view is not killed by a rounding test that reads the detail view, so probe both views.
- Transaction boundary with `open-in-view: false` and lazy `@ElementCollection`: removing the class-level `@Transactional` gives `LazyInitializationException` and a 500 on change and discontinue. Method-level `readOnly` annotations keep reads working, so remove them too (findById, search) for the read-path proof.
- An "order by removed" probe can survive by coincidence after an UPDATE: PostgreSQL appends the new tuple version, so heap order changes. Count on the tests without updates to kill it.
- "Pre-check removed" probes on a DB-backed unique constraint survive end to end, because the constraint gives the same 409. They show up only as an extra `HHH000247` in the log. Count it.
- Informational "cleaner removed" order runs are inconclusive when the last JUnit method of the earlier class commits no rows. Read the testcase order from the Surefire XML, and remember that a `[A-Za-z]+` regex drops names with digits.
- List EVERY file a probe may touch in the before-snapshot script up front. An extra probe on an unlisted file needs a separate baseline-hash proof.
- Data-only rework round: `diff` the minus-copy against the file. Its `NNNaMMM` headers give the insertion points, and from them the old-to-new line mapping for every carried-forward citation. Carry a probe forward only when at least one of its killing test methods is byte-identical. Re-run the probes whose killing test gained a row, and check that the mutant's actual list still excludes the new row (each witness hits only its own criterion).
- "Handler removed" probes: if a slice test calls the handler method directly, deleting the method is a compile error (no evidence). Remove only its `@ExceptionHandler` annotation instead; the full-context test then gets a 500.
- Ids generated by the app (random UUIDs) make an "order by id only" probe on an IT list a chance kill (survives with probability 1/n! per run). Report it as probabilistic and show the deterministic kill in the slice test that seeds fixed ids.
- Decode list-order probe failures with a small `python3 -I` script: map the ids in AssertJ's "Expecting actual ... to contain exactly" block to the letters of the expected order, so each run shows its permutation.
- A probe runner that restores every file by `cp` each round resets their mtimes to the last restore. The order proof then rests on the restore time plus the hash check, not on the implementer's write time.
- Flow boundary probes: removing a flow's class-level `@Transactional` is non-viable for any flow that loads a book (the book adapter maps the lazy `authors` inside the caller's transaction): every place dies with `LazyInitializationException ... BookJPA.authors` before any write, so a spy rollback test "survives" an equivalent mutant. Break the boundary with `@Transactional(noRollbackFor = RuntimeException.class)` instead (lazy loads still work, partial writes commit). `REQUIRES_NEW` on `StockItemDataServiceImpl.save` is non-viable too (catalogue add fails on `fk_stock_item_book`).
- Fetch-joined customer query (`join fetch o.lines ... order by`): a line-column sort orders the flat rows and keeps each order at its first appearance, so a multi-line order counts with its min (asc) and max (desc), and a book shared by two listed orders creates ties that can rescue the asserted order. Tabulate with a `python3 -I` script that enumerates tie permutations; it predicted the exact survivors. Alias the fetch (`join fetch o.lines l`) in the mutant JPQL. In a rework round, make the script parse the data from the test method (regex over the UUID, seedBook, placeOrder and setPlacedAt lines) instead of hard-coding it, take the file path as an argument, and run it on the previous round's copy as a control: it must reproduce the survivors observed there, which proves the parser is not vacuous.
- Probe flake: a run where every test errors in 0 s with `FlywaySqlUnableToConnectToDbException ... PSQLException: The connection attempt failed` is a Testcontainers start failure, not a kill. Re-run once under a new log id, and report both runs. Runner trap: re-running a probe id with another `-Dtest` overwrites its log; give each (probe, test class) pair its own id.
- Implementers sometimes run probes themselves by editing production files. Hash-check every production file against the task baselines before your own probes, and report the edit as a process note.
- Import/command IT with a mocked outbound port (one shared context): probe three families in one generator run: flow order and value relations (override vs recommended below/equal/above, raw vs normalised ISBN at each call, check moved before/after the remote call), handler annotation and status/title/code/detail swaps, plus hard-coded-detail handler mutants. The IT alone leaves hard-coded handler details alive (one value per exception); run those survivors against the web-slice test class before calling them gaps. About 35 s per probe with `clean`, 43 probes about 25 min in the background.
- A temporary witness class extending `IntegrationTestBase` (printing status, row counts per table and body per case) answers "any 500 or stray row?" for DTO shapes the IT skips (empty/blank/6 authors, USD, null price/genre, sub-cent overrides); a race witness uses a Mockito `thenAnswer` that adds the same ISBN over HTTP mid-call (gives 409 via the unique constraint). Column names come from the Flyway SQL (`price_amount`), not the DTO.
- Live smoke of an `.http` file: a `python3 -I` driver parses the `###` blocks itself and substitutes `client.global.set` ids; negative control is a `sed`-mutated copy (valid ISBN-13 with a new check digit) that must exit 1 naming the 404. `spring-boot:run` for both apps, then `kill` the java PIDs (not only the mvnw parents) and `docker compose -f bookstore/compose.yaml stop` to restore the pre-run state.
- "Row unchanged after an error answer" claims in a `@Transactional` flow hold through rollback alone, so a plain state change before the throw is equivalent. Probe the double mutant instead: change plus save plus rethrow, with method `@Transactional(noRollbackFor = <ThatException>.class)`. A reset-style change is a no-op from one starting state, so a test that starts in that state lets it survive; check the start of each error-path test per exception type (C0-17 both starts). Boundary twin for a boolean flag: the opposite-direction mutant (a "set", e.g. a no-op stocktake `correct(new Quantity(item.onHand()), ...)` that runs the once-per-dip signal at the reorder level), which must die at the OTHER parameter index; quote the `(boolean)[n]` line per probe. Prove a fix with a patched test copy installed by a script that restores by `cp -p`; in the next round `cmp` the live file against that copy.

- Bugfix negative control on ONE small production file with 5+ mutants: one probe script `<id>` that checks live == `.fixed` hash first, builds the mutant by `perl -0pe` (or `cp` of the `git show HEAD:` base for the control), runs `clean test -Dtest=<Class>` under with-budget, `cp -p` restores, and greps summary plus hash/porcelain flags. About 8 s per probe with `clean`. Print `diff fixed mutant` into the log and check it (a regex that silently does not match would otherwise give a "survivor" that is really the unmutated code; the script aborts when mutant == fixed). Mutants that keep one half of a two-part fix (noStore with the date validator off) kill only the other half's test; list which test kills which.
