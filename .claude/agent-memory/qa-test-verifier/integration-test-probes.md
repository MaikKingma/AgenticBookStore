Rule: in a combined-criteria search scenario, every criterion needs a data row that only THAT criterion excludes; probe each one by dropping it at the adapter (pass `null`).
**Why:** spec-pack scenario data is often redundant: in "author=austen&genre=FICTION" every fiction book was by Austen, so dropping `author` left the exact list green. The slice test killed the drop, the full-context scenario did not.
**How to apply:**
- For each filter ask which row would appear if the filter were gone; none = survivor. Prove with a temporary witness class extending `IntegrationTestBase` (same context, no extra Started line): passes on real code, fails on the mutant, then `rm`.
- View probes: check which endpoint the asserting test reads (`GET /books/{id}` detail view vs `GET /books` list view); a price-format probe on the list view is not killed by a test reading the detail view.
- With `open-in-view: false` and a lazy `@ElementCollection`, removing the class-level `@Transactional` gives `LazyInitializationException` and a 500 on change and discontinue; method-level `readOnly` annotations keep reads working, so remove them too for the read-path proof.
- "Pre-check removed" on a DB-backed unique constraint survives end to end (same 409); the only trace is an extra `HHH000247` in the log: count it. "Handler removed": if a slice test calls the handler directly, deleting the method is a compile error (no evidence); remove only its `@ExceptionHandler`, the full-context test then gets a 500.
- Flow boundary: removing a book-loading flow's class-level `@Transactional` is non-viable (`LazyInitializationException ... BookJPA.authors` before any write, so a spy rollback test "survives" an equivalent mutant). Break the boundary with `@Transactional(noRollbackFor = RuntimeException.class)` (partial writes commit). `REQUIRES_NEW` on `StockItemDataServiceImpl.save` is non-viable too (`fk_stock_item_book`).
- "Row unchanged after an error answer" in a `@Transactional` flow holds through rollback alone, so a plain state change before the throw is equivalent. Probe the double mutant: change plus save plus rethrow with `@Transactional(noRollbackFor = <That>.class)`. A reset-style change is a no-op from one starting state: check the start state of each error-path test per exception type. Boundary twin for a boolean flag: the opposite-direction mutant (a no-op stocktake `correct(new Quantity(item.onHand()), ...)` running the once-per-dip signal at the reorder level) must die at the OTHER parameter index.
- Bugfix negative control on ONE small production file with 5+ mutants: a probe script per `<id>` checks live == `.fixed` hash first, builds the mutant by `perl -0pe` (or `cp` of `git show HEAD:` for the control), runs `clean test -Dtest=<Class>` under budget, `cp -p` restores, greps summary plus hash/porcelain flags (about 8 s each). Print `diff fixed mutant` into the log and abort when mutant == fixed (a non-matching regex otherwise yields a "survivor" that is the unmutated code). Mutants keeping one half of a two-part fix kill only the other half's test: list which test kills which.
- Flyway history guard probes (test resources on the classpath): one runner per probe id with an EXIT trap that moves `src/test/resources/db` AND `target/test-classes/db` out and restores the test file and `application-test.yml` from SHA copies; `cp` (not `cp -p`) so the restored source is newer than its class. Probes cutting history short (`spring.flyway.target`) make Hibernate validation fail so every test ERRORs on context: non-informative, not a kill. Seed probes (`R__`, extra location) fail on the repeatable-row count, not the version list.
- Probe flake: every test erroring in 0 s with `FlywaySqlUnableToConnectToDbException ... The connection attempt failed` is a Testcontainers start failure, not a kill: re-run once under a new log id and report both. Re-running a probe id with another `-Dtest` overwrites its log: one id per (probe, class).
