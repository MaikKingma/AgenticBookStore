Traps that recur across specs in this repo. Write them into every qaDirective that touches them.

1. **"Clean working tree" before the gate.** Nothing is committed before the QA gate, so the tree always holds the impl's uncommitted changes. Never ask for an empty `git status`. Ask for `git status --porcelain` plus `shasum -a 256` of the probe-touched files, identical before the first probe and after the last restore. Verifiers have read-only git: they restore with Edit or rm, never checkout or stash.
   **Why:** a literal "clean tree" criterion cannot be met, and a verifier ends up either failing wrongly or hand-waving it.
   Plan drafts also write it into impl criteria ("restored with `git checkout`, tree clean"): impl agents have read-only git too. Flag it at Gate 1 with the snapshot rewrite.

2. **Path-reference ban vs `.gitignore`.** The team rule "no file references docs/spec-pack, agent-os, .claude, CLAUDE.md" (spec 09 strips them from `main`) collides with the root `.gitignore`, which must keep its `.claude/...` ignore entries. Every grep gate needs that exemption spelled out. In the spec PR diff on `factory`, agent files ride along (`.claude/agent-memory/**`, `agent-os/specs/**`), so whole-diff greps for qa-final run on product files only (diff minus `.claude/` and `agent-os/`). Report agent-file hits as findings for the orchestrator. The harness MEMORY.md index format uses em dashes.

3. **A probe must fail for the stated reason.** Make the verifier quote the failing assertion or exception line. Examples: a missing-migration entity without `@Id` fails as a mapping error, not as schema validation; a compile error is never a negative control. Deleting a handler method that a unit test calls directly is a compile error: write "advice live" probes as annotation removals (`@ExceptionHandler` dropped, method kept); spec 03 T9 J8 was unrunnable as written.
   Probe restores through the Edit tool can leave a stray form, because the tool trims trailing whitespace in `old_string`/`new_string`. A stray non-equivalent restore contaminates the next probe's kill. Direct verifiers to check `shasum` against the snap-before line after every restore, before the next probe, and to quote it per probe. Better: restore by `cp` from the `.orig` copy (item 20) and then `shasum`; that is byte-exact by construction.

4. **ArchUnit vacuity (allowEmptyShould everywhere).**
   - Every rule passes on empty packages, so the production run needs negative controls: a violating class in a real layer package, and a root-package class touching domain.
   - The self-test's production sanity check must read `@AnalyzeClasses` reflectively, because a hard-coded copy misses a package typo.
   - String-typed predicates (annotation FQN, package names) are silently vacuous when misspelled. Only a fixture-backed per-rule case catches that.
   - "At least one violator per rule" is too weak for a rule with several package strings (rule 5: `jakarta.persistence..` plus `org.springframework.data..`): one violator per string, or deleting the other string survives. Write that into the self-test criterion at strategy time.
   - `areAnnotatedWith` matches direct annotations only; `areMetaAnnotatedWith` also matches direct ones. Decide at strategy time which one the criterion asks for.
   - Never write "failure details contain the expected FQN" into a self-test criterion. ArchUnit details name origin AND target, and fixture chains across layers (A in query uses B in command, C in data uses A) make a designated violator the target of a neighbour rule. A one-token layer swap among near-identical rules then survives. Ask for an origin-anchored match (first `<...>` token starts with the FQN) plus `getDescription()` pinned per rule. Pinned descriptions also catch shared-instance stacking (stricter rules) and allowlist or suffix widening, which one sampled violator per rule cannot catch.
   - Completeness by reflection over `@ArchTest` fields misses `@ArchTest` methods. Add "declares no @ArchTest method" to the criterion.
   - Layered descriptions render each constraint as `where layer '<name>' may ...` (javap of 1.5.1); the layer definition lines also contain `layer '`. Count or pin `where layer '`, never the bare token.
   - A parameter predicate ("any parameter is double or float") needs four position witnesses, each its own fixture class (the origin regex accepts any member of a class, so a second member does not help): lone parameter (kills `size() > 1 &&`), first of several (kills `skip(1)`), middle of three (kills last-only and first-only), last (kills first-only). Single-parameter fixtures alone let an exact-list `haveRawParameterTypes(double.class)` pass, so keep multi-parameter ones too. Include a method and a constructor. Pin all four in the Gate 1 fixture wording; pinning only "middle" cost spec 02 two plan amendments.
   - A CompositeArchRule that repeats one package list per half needs every occurrence falsified: a fixture per package per half, or a per-half description pin (for example the full bracket occurs once per half). A set comparison over the whole description hides a drop from one half.

5. **Framework warnings vs task sequencing.** The verifier rule "green with a framework warning = FAIL" collides with skeleton-first specs: the first task's referee prints warnings that later tasks fix. At strategy time, give every expected warning an owning acceptance criterion. Known ones on this stack: Mockito inline-mock self-attach on JDK 25 (dynamic-agent and CDS warnings, fixed by a Surefire `-javaagent` argLine), JPA open-in-view, Flyway "No migrations found". Also the Maven `prefixes.txt` 401 warnings, which come from repositories declared in the pinned flyway-parent POM and are not machine-local. Put a warning-inventory item in C0: every warning quoted and classified as fixable here (FAIL), owned by a named criterion, or unowned (flag it).
   **Why:** otherwise verifiers wave warnings through as "environmental" or "owned elsewhere", and no task ever fixes the unowned ones.
   A test that provokes a constraint violation on purpose makes Hibernate log `HHH000247 ... SQLState: 23505` as WARN. Pre-classify it at strategy time as accepted, but only at an exact count and with its key, so a second, real one cannot hide behind it.
   The inventory grep must be `warn|deprecat|self-attach`. Mockito's line "Mockito is currently self-attaching ..." contains no "warn" and slips through a plain `warn` grep.

6. **Frontmatter timestamps are hand-written.** Agents' `updated`/`created` values have run minutes ahead of the real file write. Prove "the referee ran after the impl finished" with `stat` mtimes (impl artifact, last product file, Surefire XML), and direct verifiers to do the same.
   **Why:** the lens-2 ordering check and stale-agent detection both silently trust a value nobody took from the clock.

7. **Scope argument instead of a directive item.** Verifiers skip global greps as "untouched by this diff". Accept that only with a quoted scope proof plus my own cheap confirmation, and direct them to execute every global item literally.

8. **Probes that remove a file need `clean`.** `./mvnw test` without `clean` keeps a moved migration or a deleted probe class in `target/`, so the probe passes falsely or the next probe fails for the previous one's reason. Write `clean test -Dtest=...` into every probe item.

9. **Shared test-infrastructure hooks need a guard test, not a code-review fallback.** A "report whether removing `@BeforeEach` fails a test, else inspection" item leaves the hook unguarded, and once accepted at strategy time I cannot REJECT on it later. Demand a guard at strategy time instead: a `@TestInstance(PER_CLASS)` subclass seeds a row in `@BeforeAll`, and its test asserts the row is gone. Check also what a fixture really exercises: FK-linked tables truncated in ONE statement do not need CASCADE, and CASCADE masks a partial table list. Require an unlinked table.

10. **Verifiers of one session share one scratchpad.** Generic evidence names (`referee.log`, `snap-before.txt`, `n1.log`) get overwritten by the next task's verifier, so an earlier review's evidence can no longer be checked again, and a verifier can cite a stale file. Put "task-prefixed scratch file names, cited by absolute path" into C0 at strategy time. In reviews, check the evidence file's mtime against the verdict before trusting it. Task prefixes still collide across specs run in one session (spec 02 left `t1-qa-r2-*` that spec 03's T1 needed): prefix with the spec number too (`s03-t1-qa-...`), and for helper scripts in `.claude/comms/tmp` as well (unprefixed `qa-final-*.sh` from earlier specs sat there in spec 04). Also, `rg` is not on PATH inside `bash <script>` runs (exit 127): direct every `rg` item to run in the Bash tool itself.

11. **Annotation greps match Javadoc.** `grep '@'` over Java sources hits inline tags such as `{@code ...}`. Use `grep -nE '^\s*@|^\s*import '` and read the files; the class-file check (`javap -v`, no `Runtime*Annotations`) misses SOURCE-retention annotations. `\s` works in macOS `grep -E` but silently matches nothing in `git grep -E`: write `[[:space:]]` in any `git grep` item and demand a control that bites.

12. **CI run ids in a qa-final brief.** Ids handed over by the orchestrator can belong to a task branch, not the spec tip. Never write run ids; write `gh run list --commit <tip>` and `gh run view <id> --json headSha`. The `pull_request` run's `HEAD is now at <sha> Merge <tip> into <base>` line proves the merged tree.

13. **Base moved during the cycle.** An owner commit on the base breaks `merge-base --is-ancestor`. The fix is a merge into the spec branch (never rebase or force-push). Re-run the tip-identity items (fresh clone, counts, git facts, PR readiness, CI on the tip); carry the rest forward only with `git diff --name-status <old tip> <new tip>` showing no product file. The finalize commit moves the tip again: repeat the same check before the human merge.

14. **Integration integrity at the final review.** Record each task's sha256 baselines in the ledger matrices; at final-review, hash the gated files at the spec tip and compare. One command proves that squash merges and base merges altered nothing a gate reviewed.
   Verifiers write baselines in mixed forms (absolute and relative paths, `git status` header lines), and rework rounds supersede single entries. So at strategy time C0-1 must ask for repo-relative `shasum` lines only. In the brief, name the authoritative file per task, state the exact count of expected superseded FAILED lines, and dry-run the check yourself (filter `^[0-9a-f]{64}  `, strip the absolute prefix). In the same script, compare the sorted union of baseline paths with the product files of the spec diff (minus `.claude/`, `agent-os/`): an empty `diff` proves every shipped file passed exactly one gate, which the hash check alone cannot show. Run the qa-final hash check inside the fresh clone (committed bytes), not the working tree.
   Planned test names in a shape.md scenario map go stale in most tasks. At strategy time, require each implementer to update its rows (or declare the outbox map the record), and dry-run a `void <name>(` grep before the brief. Include digits in the name regex: `[A-Za-z]+` silently skipped every `...To409` name.

15. **Test data that cannot falsify the criterion.** Check the data of every listed test, not only its name:
   - Combined filters: each criterion needs a row that only it excludes. If every author match shares the genre, a dropped genre filter passes.
   - Order claims ("422 before 409", "discontinued before range") need a case where both failures are present.
   - A round trip through one mapper misses a symmetric column swap; demand one raw JDBC read of the stored row.
   - Sort and cap tests need rows inserted out of the expected order. For a multi-key sort, this holds for every key, the tiebreak included. Two errors on one field, supplied in message order, let a field-only sort pass. An order-preserving claim ("author order kept") needs input that is not already sorted, or an added `sorted()` survives. Check the pinned example values in criteria too: "Jane Austen, Mary Shelley" is alphabetical. Never write "neither id nor available order": implementers avoid exactly the named columns and leave another one ascending (spec 03 T4 stub ascending in on hand and reserved, so a re-sort by either survived). Write "sorted in no column, in either direction", which needs three rows or more (two rows are always sorted one way in every column), plus one row on the producer's filter boundary so an added stricter re-filter fails.
   - "Column" means every attribute of the ordered element and of the entity it stands for that the code holds in scope (a BookDTO map, line snapshots), not only the asserted record's fields; say so in C0-16 and list the reachable attributes per sort site in the probe list. Check shared fixture constants once: spec 04 T4 BOOK_1..3 had ISBNs descending in id order, so every id-order test was monotone in isbn and isbn sorts survived at four sites (cost the last rework round). Before writing a Required Action literal for a shared constant, tabulate it in EVERY order the tests assert over it (the stored or request order as well as the sorted order): my T4 fix made book-id order non-monotone but the stored order ascending; the orchestrator caught it. Exempt: loaded pre-mutation values that sit at no sort site (a loop-local DTO); a sort on them needs added carry code, and a probe killed by another test settles it.
   - The "sorted in no column" rule needs stated exemptions. A column the producer's filter makes constant (`lowStock` in a low-stock list) can only vary with a row outside the filter: fine on a mocked pass-through (spec 03 T7, endorsed), impossible over a real producer, where the contract's own sort keys are sorted by definition too. Name the exempt columns per test. A column every app write path keeps constant (currency EUR) is exempt on the same terms, never by "the domain rejects it on restore" when the read path does not restore. Elements that hold a child list (an order with lines) need a bound written into C0-16 at strategy time: the element's own components and accessors count; child attributes reached by a positional pick (first line's book id) count only when the sort statement already holds them flat (fetch join). Without it verifiers open unbounded probe families (spec 04 T6, A3). UUID columns: Java `UUID.compareTo` is signed on the high 64 bits, PostgreSQL `uuid` order is unsigned bytewise, so ids starting 8 to f order differently; make every column-sequence argument name its comparator and treat only a run as evidence. Cheapest fix in the data: test ids whose first hex digit is 0 to 7 order the same under both comparators (spec 03 T8); write it into directives as the preferred form, plus a reversal probe for the one permutation no single-column sort gives. Over a real producer the app generates the ids, so an id-only sort mutant dies only by chance (23/24 at four rows) and tiebreak or hard-coded-level mutants cannot be forced: name the slice test with fixed ids as their owner and have the verifier run such probes paired with it.
   - "Each row once" over a collection join: Hibernate 7 removes duplicate root entities in memory, so an exact-list test at a large limit cannot see a `left join` without distinct. The falsifier needs a SQL limit that cuts into the duplicated rows: a book with two matching authors sorted first, a second match, and limit 2. Name it in the falsifier list.
   - On PostgreSQL, removing an HQL `escape '\'` clause is equivalent (backslash is the default LIKE escape), so the clause can only be an inspection item.
   - Rounding modes need both 10.005 and 10.015. A check-digit formula `(10 - s % 10) % 10` needs a valid case with check digit 0.
   - Mutation probes on annotations: removing a method-level `@Transactional` leaves a class-level one in force. Remove both, or the probe survives for the wrong reason.
   - A guard's falsifier needs input that passes every later check once the guard is gone. Otherwise a downstream check rejects it by accident. Example: an "ASCII digits only" test with U+0668 at the check-digit position is rejected by the checksum arithmetic, so the `Character.isDigit` mutant survives. A witness that works: U+0661 replacing a 5 at a weight-1 position, because `0x661 - '0' - 5 = 1580`, which is 0 mod 10. Write "a non-ASCII digit that the naive checksum still accepts" into the directive.
   - "Uses the given clock" needs a clock fixed in a past year (for example 2000-06-15) and a value that only the real clock accepts (year 2027). A clock fixed in the current real year gives the same bound as `Clock.systemUTC()`, so a code path that ignores the clock passes. Name this witness in the falsifier list of every task that hands a `Clock` on (mapper, flow).
   - A pass-through (an exception's `details` copied into a ProblemDetail, an id, a code) needs one test input whose value differs from the default constant. If every test exception has empty details, a handler that hard-codes `List.of()` survives. This is true even when the current spec only ever produces the empty value. Write "one case per pass-through with a non-default value, asserted as a literal" into the falsifier list of every adapter task, and derive this mutation in lens 4. The same holds per handler for `code` and `title`: each handler needs one case whose code and title are not that status's only catalogue entry. A String pass-through (a reason, a title) also survives an inserted `strip()`/`trim()` when no valid test value has edge whitespace. Where the payload validation and the domain rule treat whitespace differently (`@NotBlank` vs a length-only rule), that insertion makes a "never reached over HTTP" domain rejection reachable. List one valid edge-whitespace value (for example `" ab"`) per String pass-through.
   - Figures production never varies (reserved always 0, a default level 3 and quantity 10, a signal never true before the first event) let a hard-coded default survive at every layer they pass through (aggregate event, DTO, query, view). Demand a non-default value per pass-through layer, and boundary rows at limit - 1, limit, limit + 1 on a non-default limit for every copy of a threshold. Count copies per comparison site, not per layer: in spec 03 the aggregate compared `reorderLevel` in `lowStock()` and again in the `receive` reset; I probed only the first and the verifier's own probe found the second survivor. Write "enumerate every comparison site against the limit in the diff; one default-literal probe per site" into the directive.
   - A "state unchanged" clause needs a success case starting from each value of the state (signal false and true). Tests that start only from false let an inserted reset pass, and there is no gated statement to mutate, so I cannot REJECT it later. Name both starting states in the falsifier list.
   - State-dependent rules pass vacuously when the test state never reaches the branch: "receive never registers an event" must end low and unsignalled; "restore registers nothing" must restore a low, unsignalled item. Name the state, not just the method, in the falsifier list.
   - A tiebreak in `order by` on PostgreSQL cannot always be forced by data (unspecified sort order among ties). Insert the tie pair in reverse id order and pre-declare: "must fail; if it survives three runs, inspection item". Otherwise a survivor becomes an unfair REJECT. Removal is only half of it: a tiebreak REPLACED by another column (`s.onHand`, `s.reserved`) is a real sort key and ignores physical order. Implementers pick tie rows that are ascending in every column at once, so that substitution survives (spec 03 T3 REJECT). Demand per tie group a tiebreak order that is the reverse of every substitutable column, and a substitution probe per key position, the tiebreak included. A two-row tie cannot do this (two rows are sorted one way in every column, and NULL sorts first under `desc` on PostgreSQL): ask for three rows with a nullable column's null in the middle. With a fetch join, the child collection's columns are substitutable too (`join fetch o.lines l ... order by ..., l.isbn desc`): name them in the directive, ask for one child row per tie order, and probe them; spec 04 T3 lost two rework rounds to a tie group sorted first by status and shipped time, then by line isbn and title after the implementer changed the line data of a copied witness. An index on the sort columns can supply the tiebreak, so removal survives even with reversed insertion: pre-declare it as inspection plus a final hash check of the query file.
   - `strip()` versus `trim()` needs a non-ASCII whitespace witness: U+2003, built from the code point `Character.toString(0x2003)` (see item 16). U+00A0 is no witness, because `Character.isWhitespace` excludes it. `Locale.ROOT` casing needs a run with `-DargLine="-Duser.language=tr -Duser.country=TR"`. Ask for both at strategy time if the criterion matters, otherwise they end up as inspection-only.
   - Padding witnesses ("surrounding chars in the set `trim()` strips allowed"): a witness char that the pattern's core class already accepts proves nothing about the pad class. U+2003 alone is a valid one-piece address for `[^@\x00-\x20]+`, so "U+2003 padding stays 400" was a false premise (fix-04 T2, corrected by the orchestrator). Working pair: U+001F padding accepted (inside the trim set, outside `\s`) and U+2003 next to an ASCII space rejected on each side (`em + " <addr>"`, `"<addr> " + em`), which forces the pad class to absorb U+2003. Before writing any witness, run it against the decided pattern by reading: does the core accept it?
   - "Length in UTF-16 chars" on a trimmed value cannot be a `@Pattern`: Java regex counts code points, and `@Size` sees the raw value. Plan a custom constraint (nested annotation plus validator) at Gate 1, or it costs a blocked round.
   - Framework-behaviour premises in plan prose are claims, not facts: verify against the pinned jar (`javap -c` of the validator class) before they feed a criterion or a smoke item. Hibernate Validator 9.x `@NotBlank` calls `String.isBlank()`, so U+2003 is blank (400) and U+00A0 passes; the "trims only up to U+0020" premise was false and became a refuted qa-final expectation in spec 03. A "payload accepts a non-ASCII 3-character reason" witness is U+00A0, not U+2003. Also verified (HV 9.1.5, JDK 25): `@Pattern` uses `Matcher.matches()` and `@Size` counts `length()`, both null-valid; `\s` without `UNICODE_CHARACTER_CLASS` is ASCII-only; `toLowerCase(Locale.ROOT)` turns U+0130 into two chars (the one length-growth witness). JDK premises check in seconds with a jshell script in SP.
   - A regex whose class or quantifier repeats needs one rejecting witness per position, like ArchUnit package strings (item 4): `[^@\s]+@[^@\s]+\.[^@\s]+` needs a space in each of the three parts (local, domain, top level) and an empty local, domain and top-level part (spec 04 plan G2a lists the literals). A negated class with a range (`[^@\x00-\x20]`) holds three properties per position: the excluded literal, the upper end (rejected space plus an accepted `!` per part) and the lower end (a tab per part). Spec 04 witnessed tabs and `!` only in the local part (T1 and T5), so a weakened lower end in the domain part survived and would turn a 400 into a 422 (inspection-proven, F31). List all three per position at strategy time.
   - A single production value (currency `EUR`, status `PLACED`) is a natural default too: every layer that passes it on without validating (DTO accessor, JPA mapper, view) needs one other value in its tests. A layer that hands it into a validating factory (`Money.of(amount, code)`, `valueOf`) needs a witness the factory REJECTS, asserted as the exception: an accepted value cannot tell the hand-off from a dropped argument (spec 04 T2 REJECT). Make C0-18 ask per field "plain pass-through or hand-off into a validator", and treat a missing C0-18 inventory in a verdict as a lens 1 finding. Flow translator branches HTTP cannot reach (duplicate lines, stored-data restore failures) are reachable in the flow test through a mocked port returning a corrupt stored DTO: name one case per caught type at strategy time.
   - A rule that reports one element of a list (the duplicated book, the first unknown book, the short books) needs a witness where that element is neither first nor last. My spec 04 G2d wrote A, B, A, which cannot tell the rule's choice from `get(0)`. A survivor found by the verifier cost a rework round. B, A, C, A kills `get(0)`; A, C, A, B kills `get(size - 1)`.
   - "Every rejection asserts no event" cannot be checked for a throwing factory: no instance survives, and events are per instance. Write it only for behaviour methods. For factories, give it to the publishing layer: a flow test whose rejection comes from the factory itself, with `verifyNoInteractions(events)`.

16. **Backslash-u escapes do not survive tool parameters.** A Java escape for U+2003 typed into a Write or Edit parameter lands on disk as the literal character, and a double backslash lands as two backslashes. Writing the backslash as its own escape (`u005C`, then `u2003`) lands the ASCII form. The Read output shows a literal U+2003 as a plain space, so only `od -c` or `rg '\x{2003}'` tells the two forms apart. In spec 02 this hit my own ledger and memory and the T3 witness.
   **How to apply:** state a required form as an imperative in the plan text, not as a parenthetical. Since spec 03 the decided form is a code-point constant (`Character.toString(0x2003)`), checked by `rg -n '[^\x00-\x7F]' <file>` printing nothing plus a positive control file. In reviews, check the form with `od -c`, never by reading.
   The reverse also fails: Edit cannot match a line that holds literal U+2003 characters in `old_string`, so an implementer replacing them fell back to `perl -i` (a shell-discipline deviation). When a plan asks to replace literal non-ASCII text, name an allowed method in the implDirective (Write of the whole file after Read, or a sanctioned one-line script followed by a diff check), so the deviation is not improvised.

19. **Shared test base changes and failure devices.** Adding an `@Import` or `@MockitoSpyBean` to the integration base changes the context key; if any full-context class does not extend the base, the Started count jumps by one. Check `extends` on every `@SpringBootTest` class at strategy time. A test-only failure device (rollback thrower, spy `doThrow`) needs its own non-vacuity probe: swap in the weak device (plain `@EventListener` thrower without `@Order`) or break the `@Transactional` boundary, and the scenario must fail.
   Never write the boundary probe as "remove the class-level `@Transactional`": in this repo the same annotation keeps the session open for lazy loads (`BookJPA.authors` in the book lookup), so every request dies with LazyInitializationException before any write and cannot tell "rolled back" from "never written" (spec 04 T7 J1). Write `@Transactional(noRollbackFor = RuntimeException.class)` instead; a `REQUIRES_NEW` on one save works only when its rows reference already committed data (on the stock save it hit `fk_stock_item_book`). Under that probe a BEFORE_COMMIT listener thrower still rolls back (Spring rolls back on a commit-phase exception whatever the rules say), so the device scenario needs its own probes: toggle ignored, plain `@EventListener`, recorder on AFTER_COMPLETION.

17. **Implementers probing production in rework.** A test-only implementer whose round failed on a surviving mutation tends to re-create the mutant in the production file to show its fix kills it, even after declining to do so in round 0, and even when the production file is inside its own fileScope (spec 03 T1). Put this into every test-only task's implDirective: "Never edit a file outside your fileScope, not even temporarily; mutation probes on production code are the verifier's job (describe the mutant in your outbox)." Judging rule: [[review-calibration]] item 11.

18. **Request collections (`http/*.http`) differ from the E2E inputs.** The file's sample values (hyphenated ISBN on a successful add, lowercase genre, `q` combined with a filter) are often not the combinations the integration tests send, so "the endpoints are proven by E2E" does not cover the file. In the review, diff the file's inputs against the E2E calls and name each uncovered combination as a smoke item. The smoke must replay the file's own bytes (bodies cut out with `sed -n` and sent with `curl --data @file`), never re-typed requests. Preferred form since spec 04: a `python3 -I` driver that parses the file into its `###` blocks (method, URL, headers, body line range, ids from the `client.global.set` handlers) and writes one evidence file with a CHECK line per expectation. A JSON witness body cannot carry a raw tab: it holds the `\t` escape (`od -c` shows `\ t`) and the check runs on the decoded value. `ijhttp` is usually absent, so the JetBrains `> {% %}` handler syntax stays an inspection-only residual. Smoke expectations (statuses, bodies) come from controller annotations or asserting tests, never from the impl artifact's request table (spec 03 T10 wrote 201 for a 202 add). Request comments that state results (a total, stock left, a status) are claims too: the directive asks to trace each to an asserting test or a smoke item (spec 04 T8 directive omitted it; I checked by reading).
   With `spring-boot-docker-compose` on the classpath, `spring-boot:run` starts `compose.yaml` and stops it with `stop`, not `down`, by default. A stopped leftover container comes back with old rows, so "exact search result on a fresh database" fails for the wrong reason. In the smoke preflight, check `docker compose ... ps -a`, and `down` any leftover first. Also use the smoke to close inspection-only residuals cheaply: constraint names via `pg_constraint`, untested query parameters, null-list guards.
   PostgreSQL 18 catalogues NOT NULL as `pg_constraint` rows (contype `n`, named `<table>_<column>_not_null`): a "exactly these constraint names" query needs `and contype <> 'n'`, and the `n` rows are a free nullability witness per column. A live app answers malformed JSON with Boot's error JSON (`timestamp, status, error, path`), not the empty body MockMvc shows: word accepted defaults per layer.
   Brief expectations that are counts (files per kind, test classes per annotation) come from a dry-run command, never mental arithmetic: ArchUnit classes hold `@ArchTest`, not `@Test`, so a source list needs `@(Test|ArchTest)`. Count subclasses with `grep -rln "extends <Base>"`, not from memory. An "empty snapshot expected" in a brief is false when my own memory edit sits in the tree: write memory before the dry run, or name my agent files as expected.
