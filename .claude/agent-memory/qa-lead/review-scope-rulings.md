Siblings: [[review-calibration]], [[review-survivor-rules]]. Strategy-side prevention: [[qa-directive-traps]].

1. **Required forms stated as parentheticals.** A form requirement (an escape, a specific API) that reached the plan only in parentheses is no REJECT bar when the property it serves is proven on the gated bytes: follow-up plus hash baseline until merge. Fix at strategy time: imperatives with a check command. Same, minus "property proven", for a form living only in a binding strategy decision that never reached the card or falsifier list: ENDORSE, report the undisclosed deviation, log a residual. Prevention: copy every binding decision's form into the implementing task's falsifier list.

2. **A brief expectation refuted by evidence.** When a verifier shows an expected value in my directive came from a false premise, ENDORSE lowers no bar if no criterion pins the value, the binding property still holds and I confirm it myself (one read-only check such as `javap -c` plus reading the rule), and the verifier backs the refutation with a control (U+00A0 gives 202 where U+2003 gives 400). Fix the premise at finalize and correct my ledger and memory. If a criterion pins the refuted value, it is a product question. Same family (ENDORSE plus a plan-level amendment recommendation, no bar lowered):
   - A C0 warning-class example whose only fix breaks a pinned criterion (a logback status line from a spec-mandated empty pattern): exact-count acceptance is fine when stdout is tested unfiltered and the count bites both ways; product residual.
   - A must-fail probe that cannot run as written or is an equivalent mutant (confirm by `javap` plus a witness diff): the verifier's substitute is valid when it breaks only the property under test and fails at the scenario's state assertions. If the pin is my own rewrite, I rule it: ENDORSE plus an amendment with exact wording, provided the corrected probe dies.
   - The opposite: a fail-closed premise I wrote into an RA that the verifier refutes with builds while a closed grading rule I also wrote FAILs the task. The grading rule governs; reclassing refuted cases as residual narrows the bar after the fact, which only a human may do. AMEND the RA, own the premise in the ledger, give the human options with a structural guard.
   - A harness mandate (attribution footer's emoji under "PR body ASCII only") is accepted when the prose is ASCII and no criterion pins the body. A base merged mid-sweep adding a hit to a directory-wide grep is no finding when `git grep` on both bases attributes it and the file is outside the spec diff. A base moving AFTER a qa-final PASS is no CHALLENGE when `git log --stat <old>..<new>` touches no file of `git diff --name-only <old>...<tip>`.

3. **Orchestrator-approved deviations on a refuted premise.** When the orchestrator approved a departure from a card bullet for a factual reason a verifier then refutes and every criterion still holds: ENDORSE, return the decision with the refuted premise and the cheapest restoring path (a later task's one-line fileScope amendment). Scope is the orchestrator's. Scratch-layer assertions pinning such a decision are re-pointed before qa-final re-runs them.

4. **A verification task that finds a product defect outside its fileScope** is ENDORSEd, not REJECTed, when the record discloses it truthfully, the verifier reproduced it and the orchestrator assigned a fix task. State that the ENDORSE certifies the verification, not the failing property; the fix task and qa-final close it live and refresh every record line and screenshot it makes stale. A qa-final report-only observation (a reload during a held order) is a Gate 2 residual, not a fix task, when it lies outside every criterion's scope, behaves the same on the base and its real fix needs a product decision: name the decision and options.

5. **Classing nits in authored docs and rehearsal rows.** A false statement in the task's own file is a FAIL when it can change what the reader does or concludes (provenance claim, code-naming rule, locale equivalence, a literal compared with output). A clerical pointer contradicted by its citing documents, an incomplete summary list whose omitted item carries its own label, or an omitted step whose row keeps a working judge is a correction follow-up, not a late-round REJECT. Ask the verifier to class each nit; check the environment the product really uses before accepting an environment nit.

6. **A live check whose data cannot discriminate.** A journey comparing page figures with the API proves nothing about "server figures, not the estimate" when seeded data makes both equal. ENDORSE when the verifier discloses it and names the discriminating unit witness, which I read; in a final brief ask for that witness by file:line. Isolation premises: never "one named container", never "full `docker ps -a` identical" (parallel cycles). Write: names-only listings before and after, own container absent after, every diff name quoted as foreign (reported, never touched), the shared container's `State.StartedAt` identical.

7. **"Same wording elsewhere" in a comment-fix task.** Tell a class claim (a code-formatted class named as the rule's holder, false) from a layer claim ("the flow owns it"), and grep earlier plans for a criterion pinning the wording. A pinned, true layer claim is no blast-radius gap: ask for a "checked, consistent" line in bug.md. For a pack-wording bug grep all of `docs/spec-pack/` myself; a hit outside the authorised lines is a question to the orchestrator plus a qa-final attribution item. Build a final-brief "expected hits" list by running the grep myself and attributing every hit.
