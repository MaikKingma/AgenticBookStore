Rules I settled while meta-reviewing verifier verdicts in this repo's SDD cycle. Apply them in every review so verdicts stay consistent across tasks and specs. See also [[qa-directive-traps]].

1. **Carrying probe evidence into a rework round.** A verifier may skip re-running the earlier round's mutation probes only if all three of these hold:
   - (a) the sha256 of every production file equals the earlier baseline;
   - (b) the test diff is insertion-only, which I check by finding every earlier quoted asserting line verbatim at its recorded or shifted line (the shift equals the inserted block);
   - (c) the earlier probe logs are still on disk.

   **Why:** a mutant's kill depends only on the production bytes and on the killing test. Re-running is wasted budget, but an edited killing test silently voids the old evidence.
   **How to apply:** this is why I quote asserting lines into the ledger every round. If any of (a) to (c) fails, CHALLENGE for a re-run.
   A verifier can prove (b) without my quotes: it copies the test file, deletes the inserted method and hashes the result against the earlier baseline.
   Key carried probes by handler and field, not by probe ID: verifiers renumber IDs between rounds to follow the plan.
   A comment-only edit of a guarded TS/JS file (a hash pin replaced by an amendment) keeps the earlier probe kills when the comment-stripped files are byte-identical and the guarding test's hash is unchanged; close a skipped re-run probe list by that proof, not a CHALLENGE (spec 12 T7, setupTests.ts).
   An inserted-statement survivor (`if (x === null) continue`) is no REJECT when the simple mutation of the same guard dies and the policy it bends is pinned by other rows: rule 3 allowance plus a test-only follow-up.
   An input-only edit (data reordered, no asserting line changed) also keeps the carry. It is proven the same way: undo the edit in a copy and hash it. It holds only if no carried probe has the edited test as its only killer, or the edit keeps that probe's output different from the expected value. A non-probe check that depends on state across test classes (order independence) carries forward under the same conditions only when the inserted test writes fresh keys inside a rolled-back slice transaction after the cleaning hook. For a committing integration test, it also carries when the added rows sit in existing methods of a class that cleans before each test, and the Surefire XML method order shows that the last executed method is unchanged and commits nothing.

2. **Null guards count as validation branches.** In domain and domaininteraction code, an `Objects.requireNonNull` guard, or any null check that throws, needs a test that fails when it is removed. The exception is when the removal is equivalent: a later statement throws the same exception type on the same input (for example `List.copyOf(null)`, or a dereference of the field inside the constructor).
   **Why:** without the guard, an aggregate with a null field gets built silently, and no test notices.
   **How to apply:** feed this forward to impl directives so the tests get written up front, not after a FAIL.

3. **REJECT threshold for surviving mutations.** On money, ISBN or numbering, persistence, transaction and cross-module contract criteria, a surviving mutation I can show from the code is a REJECT.
   On a low-risk criterion, a survivor that only distinguishes the decided wording (`strip()` vs `trim()`, `Locale.ROOT` vs the default locale) gets different treatment when the strategy listed no falsifier for it and the code holds the decided form. I verify it by reading, record it as inspection-proven, and feed forward a witness for later tasks.
   **Why:** the strategy's falsifier list is the advance bar. Spending the last rework round on a cosmetic distinction moves that bar after the fact.
   **How to apply:** prevent it at strategy time instead: name the witness in the falsifier list (see traps file item 15).
   A verifier's "equivalent under the tested requests" is no equivalence claim: find the reachable input that differs (an Accept header, edge whitespace). If only clients the cross-module consumer never is see it, and the strategy listed no falsifier, apply this allowance and feed the witness to the next task touching the same helper (spec 05 T4 CT-rm -> T5).
   Defensive path guards in an unscoped advice (a 415 guard, `getContextPath()` in the prefix) are equivalent only after I read the config myself (actuator `exposure.include`, `server.servlet.context-path`, any `consumes` outside the guarded prefix) and a witness tried the reachable routes. A prefix survivor (`/api` for `/api/`) can differ only on raw URIs with a path parameter or percent-encoding, where the mutant gives the better answer: no test should pin that side; record the raw-URI vs lookup-path gap as a plan-level residual (fix-05 T2).
   A survivor on input my own strategy priced as a residual (spec 06 R4, a title without `availability`) or that adds behaviour where no guard exists (a null first list element), with production correct by reading, gets the same allowance even on an ACL criterion. Offer a test-only follow-up task and add a qa-final probe. It is not a REJECT in the last round. A survivor of an existing throwing guard is still a REJECT (C0-8).
   The same allowance covers a survivor that is equivalent in production because of a pinned configuration, for example a mapper that ignores its `Clock` parameter while the configured bean is `Clock.systemUTC()`. It differs only under a test double. The allowance holds when the clause was an inspection item, not a listed falsifier. Then feed a witness forward to the next task that crosses the same seam, and open a follow-up for any test whose name claims the property. If that over-claiming test was the only listed falsifier, the survivor stays a REJECT.

4. **Survivor whose kill contradicts a pinned criterion.** If the only way to kill a surviving mutation is to change something an acceptance criterion pins (a fixture signature, for example), it is not a REJECT. Record it as a plan-level gap, recommend the plan amendment to the orchestrator (cheapest inside a rework round that runs anyway), and otherwise add a follow-up and a final-brief item. Say so when the pin came from my own Gate 1 rewrite. A survivor that can be killed in scope without touching a pin stays a REJECT under rule 3.
   **Why:** a REJECT whose Required Action breaks a criterion cannot be met. Scope belongs to the orchestrator.
   **How to apply:** verifiers tend to label all their own extra survivors "informational". Judge each one against the criterion text and the file scope, not against the directive's probe list.
   Same rule for an inserted `catch` around a port call in a flow test with mocked ports (the mock never throws) when the criterion lists the allowed new tests. Endorse only if a later task owns the atomicity test, and feed that task a must-fail swallow probe so its kill is proven rather than assumed.
   Same for a test helper's default wiring (a `whenTestFinishes = onTestFinished` parameter) that only a test failing on purpose can kill while C0-3 bans `.fails` outside one exemption: inspection by reading, a hash pin to the spec tip, and a feed-forward that keeps later tests from leaning on it (the client turns an unmatched request into the network alert, so network-alert tests answer through a matched throwing route and assert the call paths) (spec 12 T5, R11).
   Same again when my strategy put a clause's falsifier at qa-final (a live latency check) and the task's survivor is a dropped call there (production sleeper no-op): ENDORSE, feed the qa-final brief the check plus a control that proves it can tell the two apart, and offer a pin-respecting test-only witness as a follow-up (spec 05 T5).

5. **Strengthening-only survivors.** A mutation that can only add violations (for example ArchUnit `allowEmptyShould(true)` -> `(false)` on imports that are never empty) does not weaken the guard. If the criterion pins the setting and the strategy made it a reading item, record it as inspection-proven, not a REJECT, even on money criteria. Rule 3's no-allowance clause is for survivors that let a violation through.
   **Why:** the REJECT threshold protects the guard's direction; pinning a stricter-is-fine setting costs a rework round for no safety.

6. **Edited killing assertion vs carry-forward (rule 1 b).** An edit voids carried probe evidence unless it is a monotonic strengthening I verify in the helper: for example an expected-violator list extended with the old entries as an unchanged prefix, checked by a loop that asserts each entry on its own (no count or exact-set check). Read the helper before accepting it.
   **How to apply:** the implementer's list order decides which fixture a probe names first; demand a probe that only the new fixture can kill to show it is load-bearing.

7. **Oracle helpers that call production code.** A test may compute an expected value by calling production code (for example the domain exception's message) when three things hold:
   - (a) the helper calls nothing of the class under test;
   - (b) every contract field (code, title, field name, list, exception type) stays a literal, so the oracle only adds a check;
   - (c) the helper asserts its own precondition (for example `isNotNull`), so an upstream mutation still fails the test, only at a different line.
   A contract field computed from production code is a REJECT. The verifier's "failure lands in the helper" is not a weakness.

8. **Required forms stated as parentheticals.** If a form requirement (an escape and not a literal, a specific API) reached the plan only in parentheses, it is no REJECT bar when the property it serves is proven on the gated bytes. Open a follow-up and rely on the hash baseline until merge. The fix is at strategy time: write forms as imperatives with a check command (see [[qa-directive-traps]] item 16).
   Same, minus the "property proven" clause, for a form that lives only in a binding strategy decision and never reached the card or the T<n>-F list (spec 12 decision 10: instants "in a `<time dateTime>`", absent from every page, disclosed by nobody). Verifiers check directives, not decisions, so it surfaces only in my own read of the decisions. The same holds for a strategy quality-gate line (spec 12 G11 "disabled buttons have a visible reason") that never reached T<n>-F: report the disposition, no REJECT. ENDORSE, report the undisclosed deviation to the orchestrator (accept in an amendment or fix task) and log a residual. Prevention: at strategy time copy every binding decision's form into the falsifier list of the task that implements it, and direct verifiers to report each decision their files implement as met or disclosed.

9. **Survivors equivalent on every reachable input.** A survivor on a money-adjacent clause (for example `toString()` for `toPlainString()` on a price) is inspection-proven, not a REJECT, when four things hold:
   - an upstream invariant, pinned by its own tests (a scale-2 money type, a fixed-scale column), makes the outputs identical for every input that can reach the code;
   - the strategy made the clause an inspection item;
   - the listed falsifier (for example the trailing zero kept) is present and kills;
   - a follow-up names the witness, and the witness becomes required once a later spec widens the input domain.
   Rule 3's no-allowance clause is for survivors that change a reachable output.
   **Downstream validators are no invariant.** "Equivalent because the domain rejects other values" fails when the check sits after the mutated hand-off: a mapper that drops the currency argument (`Money.of(amount)` for `Money.of(amount, code)`) bypasses the EUR-only rule and silently relabels a stored USD price. Equivalent only if the input is already the validated type (an `OrderLine` holding a `Money`) or is guarded upstream (a check constraint); stored strings without a constraint are reachable. The plan's ProblemDetail "stored price" row names the path; look for a sibling test that kills the same mutant in an older mapper.
   **Read paths that never restore.** Flows whose reads return the port result unrestored carry corrupt stored values straight to the views, so "the aggregate keeps it consistent" is no equivalence argument there either (verifiers made this error twice in spec 04). Not every such survivor is a REJECT, though: a view clause that delegates to an accessor already pinned with a decorrelated witness (currency of the first line), where the mutant re-implements the delegate with another index, differs only on corrupt rows for which the spec defines no answer beyond the delegation. That is a rule 3 allowance plus a follow-up and a final hash check, unlike a mutant that turns a rejection the ProblemDetail table names into a silent success. Check the flow's read methods before accepting any "unreachable" claim in a view task.
   **Pass-through survivors found late.** If a later task exposes a survivor in an already-endorsed sibling (the same handler pattern), restore consistency with a must-fail probe in the qa-final directive, and offer the orchestrator a test-only fix task first. Never drop it because the sibling is merged. If you find it while reviewing an unrelated fix task, it is not a Required Action of that task (it lies outside that task's criteria). If you find it while reviewing the still-open fix task for the same class and file scope, and a run probe proves it, fold it in as a REJECT with a test-only Required Action, on condition that the orchestrator records the criteria extension in plan.md. This is cheaper than a certain qa-final FAIL plus another fix task.
   **Pass-through inventory.** For each handler, list the distinct input values the tests feed each contract field (`code`, `title`, `details`, ids). A field fed only one value survives its replacement by that value. That is a realistic mutant when the value is a natural default: an empty list, null, or the single catalogue entry for that status (a status-keyed table is the obvious wrong implementation). An arbitrary test literal that no spec names is not a realistic mutant. But grep the whole spec pack (`docs/spec-pack/specs/`) before calling it arbitrary. A 503 code that is "from the exception" in the current spec was named by later specs (one code first, then a second), so a hard-coded pair is realistic. Checking only the current spec's catalogue caused a wrong exclusion. Checking `details` alone missed `code` and `title` in two reviews.
   Single test constants (one id, one instant, one e-mail shared by every test) let hard-code mutants survive in mappers. I do not REJECT on them under this rule, but an orchestrator may bind them as Required Actions; then prevent the late round for later tasks with an implDirective data rule ("every pass-through field fed two distinct values, asserted as literals"), not with a stricter verifier bar.
   A `valueOf(status)` hand-off killed by an unknown value ("BOGUS") still lets a case-folding or `strip()` variant survive. It is inspection-proven when the writer stores `name()` and the criterion pins plain `valueOf`.

10. **No red run.** Tests written first with a green first run are not a gate finding outside an sdd-bugfix lead directive, provided every criterion clause bites on the gated bytes: a must-fail probe kills it, or I kill it by reading. Judge a clause with neither under lenses 3 and 4. The missing red run adds nothing.

11. **Implementer edits outside its file scope.** In rework rounds, implementers sometimes mutate a production file themselves to prove their fix kills the survivor. If the file is restored, the verifier's own snapshot and baseline show it hash-identical, the runs did not overlap, and the gate evidence is the verifier's own, this is a process finding for the orchestrator, not a gate finding. Implementer probe logs are never gate evidence: a verdict that leans on them, or overlapping runs, gets a CHALLENGE. Prevention wording: [[qa-directive-traps]] item 17.

12. **A disclosed probe-restore slip.** It is no finding when three things hold:
   - (a) the before and after snapshots are identical;
   - (b) every gated file's mtime is earlier than snap-after and the referee start, and its current hash equals snap-before, so the referee compiled exactly the received bytes;
   - (c) every probe run after the slip shows a failing line that the stray form cannot explain, or the stray form is equivalent. Example: a code typo left in place, while the next probe fails at the title line after the code line passed.

   If (c) fails for a probe, that probe has no evidence: CHALLENGE for a re-run. Prevention wording: [[qa-directive-traps]] item 3.
   An env-selected mutant schema (one schema file per production class, a `switch` on an env variable, `default` = the original) is valid probe evidence when a control run with the variable unset is green, I have read every `case` against its named mutant, and each probe is its own `clean test` run with its own log, restored by `cp` and hash-checked. Annotation mutants cannot be switched and need separate edits.
   Two sort probes that give the same permutation leave byte-identical failure text, so the log cannot prove which mutant ran. On a pure pass-through asserted with `containsExactly`, accept one run per distinct permutation plus the column-by-column sequence argument: the kill is a function of the stub data, which I verify by reading.

13. **A rework edit to an asserting line that follows a data edit.** Lens 6 ("changed expected value") is no REJECT when four things hold: production is hash-identical; the element set and the matcher are unchanged (the new expected value is the spec rule recomputed on the new inputs); every probe the old line killed was re-run and is still killed by some test; the edit kills more than before. Losing a redundant kill (a second test that also caught a mutant) is acceptable when the test named for that criterion still kills it with decorrelated data.
   **Why:** extra hardening asked by the orchestrator beyond my Required Action (tie data in a second test) changed the expected order; treating that as a loosening would punish a stronger test.
   **How to apply:** before endorsing, check by reading which mutants only the edited test kills (for example a level-relative order key, only visible where rows have different levels) and confirm they still die.

14. **A brief expectation refuted by evidence.** When a verifier shows that an expected value in my directive came from a false premise (a library behaviour, a count), it is no FAIL and ENDORSE lowers no bar if three things hold: no acceptance criterion pins the expected value; the binding property behind it still holds, and I confirm it myself (one read-only check such as `javap -c`, plus reading the production rule); the verifier backs the refutation with a control (for example U+00A0 gives 202 where U+2003 gives 400). Then fix the premise in the spec docs at finalize, and correct my ledger and memory. If a criterion does pin the refuted value, it is a product question for the orchestrator, not an ENDORSE.
   The same holds for a C0 warning class example ("fixable in scope = FAIL") whose only fix breaks a pinned criterion (spec 05 T6: a logback status line caused by a spec-mandated empty pattern). That is a plan-level decision for the orchestrator (rule 4). Confirming its exact-count acceptance lowers no bar when the binding property (stdout is clean) is tested unfiltered and the count bites both ways. Record the line as a product residual for the owner.
   Same for a criterion whose literal wording the orchestrator's own mandated process breaks (plan.md bookkeeping commit vs "no file outside ci.yml on the task branch"): ENDORSE when the protected property (no product file changed) is proven, and recommend the wording fix at finalize.
   The same holds for a must-fail probe that cannot run as written, or that is an equivalent mutant (confirm by `javap` plus a witness diff over methods x paths that is empty for the mutant and non-empty for the observable variant): a verifier's substitute is valid evidence when the original's log shows the other cause (the control), and the substitute breaks only the property under test and fails at the scenario's state assertions. Offer the corrected probe text as a plan amendment.
   At a fetch-joined `order by`, an `@OrderColumn` position is a flat child column reachable only as `index(l)`. Its `asc` sort ties every root at position 0, so no data can force it: treat it as an inspection item next to the removed tiebreak, not a survivor.

15. **Survivors killed by a gate grep.** Before judging a verifier's "informational survivor", check whether a common-directive gate check rejects the mutant (a clock grep that must print exactly one `Clock.system` line rejects a bean built with `Clock.systemUTC()`; a mapper grep rejects `JsonMapper.builder()` in main). Then it is gate-proven, not a survivor, as long as the grep runs in every later task and qa-final. Feed a test-pinned follow-up only if the clause is high-risk under rule 3. Verifiers miss this (spec 05 T1).

16. **"Covered one layer down" survivors in an integration-test task.** An IT over already endorsed layers often lets a flow mutant survive (an order or hand-off its data never makes visible). It counts as killed when its body equals a probe in the earlier gate's schema and the rule 1 carry holds (both hashes equal now, result line on disk). Diff the mutant against the `.orig`, find the case in the earlier schema, quote its result line. No re-run, no REJECT; a hash change makes it a qa-final re-run item (spec 06 T7).

17. **A named read-only check the verifier skipped.** Sometimes a verifier skips a named check (a contract hash baseline, an `ls -lT` listing) while a broader check it did run (whole-tree `git status`/`diff --stat`) already shows the property. I run the read-only check myself, record the result, and do not CHALLENGE. A CHALLENGE is for a missing check that needs a test run, or for evidence that contradicts itself. Also diff every reused mutant against its hash-checked `.orig` myself. Verifiers reuse mutant directories from earlier gates and sometimes say the generator is missing when it is not.

18. **A verification task that finds a product defect outside its fileScope.** A record-and-screenshots task (spec 12 T10) whose verifier reproduces a product defect (layout, a 404 resource) is ENDORSEd, not REJECTed, when the record discloses it truthfully with evidence, the verifier reproduced it independently, and the orchestrator has assigned a fix task. Say in the meta-verdict that the ENDORSE certifies the verification, not the failing property; the fix task and qa-final must close that property live, and the fix task refreshes every record line and screenshot it makes stale.
   **Why:** the task cannot fix product code inside its scope, so a REJECT has no meetable Required Action; endorsing silently would let Gate 2 read the property as proven.
