Rules settled in meta-reviews; apply them in every review so verdicts stay consistent. Siblings: [[review-survivor-rules]] (surviving mutations), [[review-scope-rulings]] (premises, scope, docs nits). Directive wording: [[qa-directive-traps]].

1. **Carrying probe evidence into a rework round.** A verifier may skip re-running earlier mutation probes only if (a) the sha256 of every production file equals the earlier baseline; (b) the test diff is insertion-only (every earlier quoted asserting line found verbatim at its recorded or shifted line); (c) the earlier probe logs are still on disk. Why: a mutant's kill depends only on the production bytes and the killing test; an edited killing test silently voids old evidence. That is why I quote asserting lines into the ledger every round. If (a) to (c) fail, CHALLENGE for a re-run.
   - A verifier can prove (b) without my quotes: copy the test file, delete the inserted method, hash against the earlier baseline, plus a control (the REJECT's survivor run against the pre-rework copy still passes). Key carried probes by handler and field or runner mutant text, never by bare ID (verifiers renumber and reuse IDs): prefix IDs with the task, point at the runner file, and diff mutant text against the earlier runner line before writing "X killed".
   - Keeps the carry: a rework changing only how a killing test captures output (asserting lines verbatim, mutants only that test kills re-run); a production edit when every carried mutant edits an untouched line and no killing input reaches the changed branch (read the rework numstat myself: "no product file changed" often means the site); a whitespace-only or comment-only edit of a guarded TS/JS file; an input-only edit (undo it in a copy and hash).

2. **Edited killing assertion vs carry-forward.** An edit voids carried evidence unless it is a monotonic strengthening I verify in the helper (expected-violator list extended with old entries as an unchanged prefix, each asserted on its own, no count or exact-set check). Demand a probe only the new fixture can kill.
   - A rework edit to an asserting line that follows a data edit is no REJECT when production is hash-identical, the element set and matcher are unchanged (the new expected value is the spec rule recomputed on new inputs), every probe the old line killed is still killed by some test, and the edit kills more than before. Check by reading which mutants only the edited test kills.

3. **No red run.** Tests written first with a green first run are no gate finding outside an sdd-bugfix lead directive, provided every criterion clause bites on the gated bytes (must-fail probe, or I kill it by reading). When a bugfix's root-cause file is the test itself, check at which line each red fixed-bytes probe fails: neighbouring lines mean the rewritten assertion has no run evidence. Unlisted in the plan and exact by reading: ENDORSE, brief one qa-final probe per direction (Flyway history: an extra location holding a V file; a `SELECT 1` V file above `spring.flyway.target`). Implementer red taken before editing pages proves the page side only: accept when the verifier's NC on the final bytes repeats the messages verbatim and explains every extra red.

4. **Implementer edits outside its file scope.** Mutating a production file to prove a fix kills a survivor is a process finding for the orchestrator, not a gate finding, if restored, hash-identical in the verifier's snapshot, runs did not overlap and gate evidence is the verifier's own. Implementer probe logs are never gate evidence: a verdict leaning on them, or overlapping runs, gets a CHALLENGE. Wording: [[qa-probe-design-traps]].

5. **A disclosed probe-restore slip** is no finding when (a) before and after snapshots are identical; (b) every gated file's mtime is earlier than snap-after and the referee start and its hash equals snap-before; (c) every probe run after the slip fails at a line the stray form cannot explain, or is equivalent. If (c) fails for a probe, CHALLENGE for a re-run. Prevention: [[qa-probe-design-traps]].

6. **Bounding the escalated round.** A survivor that differs only when a file descriptor itself fails, under a concurrent writer or a double fault, whose harm lies outside the criterion's protected property, is struck under AMEND to a follow-up plus a final gate grep (the `rm` twin of a killed `cp` restore failure stays: [[review-survivor-rules]] rule 8). Why: each round's new code yields a narrower mutant class. The escalated round gets a closed RA list, production hash-pinned, insertion-only tests ("modulo trailing whitespace": `.editorconfig` trims it), a re-run of only the batch whose cases changed, and FAIL grounds limited to unmet RAs, regressions, drift or a defect witness.

7. **A named read-only check the verifier skipped** (a hash baseline, an `ls -lT` listing) while a broader check already shows the property: I run it myself and record it, no CHALLENGE. CHALLENGE is for a missing check needing a test run, or self-contradicting evidence. Diff every reused mutant against its hash-checked `.orig` myself. Lens 2 ordering: agent frontmatter `updated` can be off by tens of minutes; order by `ls -lT` mtimes plus copy-aside hashes. A check only in a feed-forward never reaches verifiers: copy every FF check into the T<n> block.

8. **Probabilistic concurrency witnesses.** A latch-and-threads test against a removed `synchronized` is killed in some runs and survives in others. Count all runs across rounds, apply the pre-declared three-run rule literally, do the inspection myself (shared state private, touched only inside the guarded method). ENDORSE, pin the guard with a qa-final gate grep. Optional deterministic witness: a test `Clock` whose `instant()` records the maximum threads inside it while waiting on a latch nobody releases, asserted to be 1. Never spend a rework round on it.


10. **Skipped dev-mode walk (verifier definition 6(b)) on a UI fix.** For a mapping-only change in an existing render path (no new component, hook, list or DOM) whose component test renders the real page under the setupTests console trap: ENDORSE and move the walk to qa-final as a required item (Vite dev, fresh context, `page.route` with the real server body, console dump), not a CHALLENGE. A new component or list is a CHALLENGE. `page.route` needs no backend.
