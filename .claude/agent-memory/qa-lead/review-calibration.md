Rules I settled while meta-reviewing verifier verdicts in this repo's SDD cycle. Apply them in every review so verdicts stay consistent across tasks and specs. See also [[qa-directive-traps]].

1. **Carrying probe evidence into a rework round.** A verifier may skip re-running the earlier round's mutation probes only if all three hold: (a) the sha256 of every production file equals the earlier baseline; (b) the test diff is insertion-only, which I check by finding every earlier quoted asserting line verbatim at its recorded or shifted line (shift = inserted block); (c) the earlier probe logs are still on disk.
   **Why:** a mutant's kill depends only on the production bytes and the killing test; an edited killing test silently voids the old evidence. **How to apply:** this is why I quote asserting lines into the ledger every round. If (a) to (c) fail, CHALLENGE for a re-run.
   A verifier can prove (b) without my quotes: copy the test file, delete the inserted method, hash against the earlier baseline. Pair it in the rework directive with a control: the REJECT's survivor run against the pre-rework test copy must still pass, proving the inserted lines are the killers. Key carried probes by handler and field or by the runner's mutant text, never by bare ID: verifiers renumber, and two verifiers reused one ID for different mutants (spec 14 "MC11"), so I logged a survivor as killed. Before writing "X killed" from a later gate, diff its mutant text against the earlier runner line; in directives prefix IDs with the task (T2-MC11) and point at the runner file.
   Variants that keep the carry:
   - A rework that changes only how a killing test captures output (pipe to files) keeps it when the new capture sees a superset, the asserting lines are verbatim and the mutants that test alone kills were re-run.
   - A rework that edits a production file fails (a) literally; the carry still holds when every carried mutant edits an untouched line and no killing test input reaches the changed branch. Prove the second point by listing the input tokens with `git grep -oh` over the earlier tests. Verifiers write "no product file changed" when they mean the site: read the rework numstat myself.
   - A whitespace-only production edit keeps (a) in substance when I `diff` the `.orig` copy and see only spacing. A comment-only edit of a guarded TS/JS file keeps the kills when the comment-stripped files are byte-identical and the guarding test's hash is unchanged: close the skipped re-run list by that proof, not a CHALLENGE.
   - An inserted-statement survivor (`if (x === null) continue`) is no REJECT when the simple mutation of the same guard dies and the policy it bends is pinned by other rows: rule 3 allowance plus a test-only follow-up.
   - An input-only edit (data reordered, no asserting line changed) is proven the same way (undo the edit in a copy, hash it) and holds only if no carried probe has the edited test as its only killer, or the edit keeps that probe's output different from the expected value. A cross-class state check (order independence) carries only when the inserted test writes fresh keys inside a rolled-back slice transaction after the cleaning hook; for a committing IT also when the added rows sit in existing methods of a class that cleans before each test and the Surefire XML shows the last executed method unchanged and committing nothing.

2. **Null guards count as validation branches.** In domain and domaininteraction code, an `Objects.requireNonNull` guard, or any null check that throws, needs a test that fails when it is removed, unless removal is equivalent (a later statement throws the same exception type on the same input: `List.copyOf(null)`, a dereference in the constructor). **Why:** without the guard an aggregate with a null field is built silently. **How to apply:** feed forward to impl directives so the tests are written up front.

3. **REJECT threshold for surviving mutations.** On money, ISBN or numbering, persistence, transaction and cross-module contract criteria, a survivor I can show from the code is a REJECT.
   On a low-risk criterion, a survivor that only distinguishes the decided wording (`strip()` vs `trim()`, `Locale.ROOT` vs default) gets different treatment when the strategy listed no falsifier and the code holds the decided form: verify by reading, record as inspection-proven, feed forward a witness.
   **Why:** the strategy's falsifier list is the advance bar; a cosmetic distinction in the last rework round moves it after the fact. **How to apply:** prevent it at strategy time by naming the witness ([[qa-directive-traps]] item 15).
   The same allowance (inspection plus a test-only follow-up and a qa-final probe, no last-round REJECT) covers:
   - An exemption the code never names (one label carved out of a generic loop whose siblings are pinned), when a real-page probe shows the gated checker flags the input: send the case to the last task owning the files before a freeze.
   - A verifier's "equivalent under the tested requests": find the reachable input that differs (Accept header, edge whitespace); if only clients the cross-module consumer never is see it and no falsifier was listed, apply the allowance and feed the witness to the next task on the same helper.
   - Defensive path guards in an unscoped advice (a 415 guard, `getContextPath()` in a prefix) are equivalent only after I read the config myself (actuator `exposure.include`, `server.servlet.context-path`, `consumes` outside the prefix) and a witness tried the reachable routes. A prefix survivor (`/api` for `/api/`) differs only on raw URIs with path parameters or percent-encoding, where the mutant gives the better answer: no test should pin that side; record the raw-URI vs lookup-path gap as a plan-level residual.
   - A survivor on input my own strategy priced as a residual, or that adds behaviour where no guard exists (null first list element), with production correct by reading, even on an ACL criterion. A survivor of an existing throwing guard is still a REJECT.
   - A survivor equivalent in production because of a pinned configuration (a mapper ignoring its `Clock` parameter while the bean is `Clock.systemUTC()`), when the clause was an inspection item, not a listed falsifier: feed a witness to the next task crossing the seam and open a follow-up for any test whose name claims the property. If that over-claiming test was the only listed falsifier, it stays a REJECT.

4. **Survivor whose kill contradicts a pinned criterion.** If the only way to kill a survivor is to change something a criterion pins (a fixture signature), it is no REJECT: record a plan-level gap, recommend the plan amendment (cheapest inside a rework round that runs anyway), otherwise add a follow-up and a final-brief item. Say so when the pin came from my own Gate 1 rewrite. A survivor killable in scope without touching a pin stays a REJECT under rule 3.
   **Why:** a REJECT whose Required Action breaks a criterion cannot be met; scope belongs to the orchestrator. **How to apply:** verifiers label all their extra survivors "informational"; judge each against the criterion text and file scope, not the directive's probe list.
   Same for: an inserted `catch` around a port call in a flow test with mocked ports when the criterion lists the allowed new tests (endorse only if a later task owns the atomicity test; feed it a must-fail swallow probe); a test helper's default wiring (`whenTestFinishes = onTestFinished`) that only a deliberately failing test can kill while a C0 item bans `.fails` outside one exemption (inspection, hash pin to the spec tip, feed-forward that later tests do not lean on it); a clause whose falsifier my strategy put at qa-final (a live latency check) when the survivor is a dropped call there: ENDORSE, brief qa-final with the check plus a control that tells the two apart, offer a pin-respecting test-only witness.

5. **Strengthening-only survivors.** A mutation that can only add violations (ArchUnit `allowEmptyShould(true)` -> `(false)` on never-empty imports) does not weaken the guard. If the criterion pins the setting and the strategy made it a reading item, record it as inspection-proven, even on money criteria. Rule 3's no-allowance clause is for survivors that let a violation through.

6. **Edited killing assertion vs carry-forward (rule 1 b).** An edit voids carried probe evidence unless it is a monotonic strengthening I verify in the helper (expected-violator list extended with the old entries as an unchanged prefix, checked by a loop asserting each entry on its own, no count or exact-set check). Read the helper first. Demand a probe only the new fixture can kill to show it is load-bearing.

7. **Oracle helpers that call production code.** A test may compute an expected value from production code (the domain exception's message) when (a) the helper calls nothing of the class under test; (b) every contract field (code, title, field name, list, exception type) stays a literal; (c) the helper asserts its own precondition (`isNotNull`), so an upstream mutation still fails the test, only at another line. A contract field computed from production code is a REJECT. "Failure lands in the helper" is no weakness.

8. **Required forms stated as parentheticals.** A form requirement (an escape and not a literal, a specific API) that reached the plan only in parentheses is no REJECT bar when the property it serves is proven on the gated bytes: open a follow-up and rely on the hash baseline until merge. Fix at strategy time: imperatives with a check command ([[qa-directive-traps]] item 16).
   Same, minus "property proven", for a form living only in a binding strategy decision or quality-gate line that never reached the card or the falsifier list (instants "in a `<time dateTime>`", "disabled buttons have a visible reason"). Verifiers check directives, not decisions. ENDORSE, report the undisclosed deviation to the orchestrator (accept in an amendment or fix task), log a residual. Prevention: copy every binding decision's form into the falsifier list of the implementing task and direct verifiers to report each decision their files implement as met or disclosed.

9. **Survivors equivalent on every reachable input.** A survivor on a money-adjacent clause (`toString()` for `toPlainString()`) is inspection-proven, not a REJECT, when: an upstream invariant pinned by its own tests (scale-2 money type, fixed-scale column) makes outputs identical for every reachable input; the strategy made the clause an inspection item; the listed falsifier (trailing zero kept) is present and kills; a follow-up names the witness, required once a later spec widens the input domain. Rule 3's no-allowance clause is for survivors that change a reachable output.
   **Downstream validators are no invariant.** "Equivalent because the domain rejects other values" fails when the check sits after the mutated hand-off: a mapper dropping the currency argument (`Money.of(amount)` for `Money.of(amount, code)`) bypasses the EUR-only rule and relabels a stored USD price. Equivalent only if the input is already the validated type or guarded upstream (a check constraint); stored strings without a constraint are reachable. Look for a sibling test killing the same mutant in an older mapper.
   **Read paths that never restore.** Flows whose reads return the port result unrestored carry corrupt stored values to the views, so "the aggregate keeps it consistent" is no equivalence argument (verifiers erred twice). Not every such survivor is a REJECT: a view clause delegating to an accessor already pinned with a decorrelated witness, where the mutant re-implements the delegate with another index, differs only on corrupt rows with no spec answer beyond the delegation: rule 3 allowance plus follow-up and final hash check; unlike a mutant turning a rejection the ProblemDetail table names into a silent success. Check the flow's read methods before accepting any "unreachable" claim in a view task.
   **Pass-through survivors found late.** A survivor exposed in an already-endorsed sibling (same handler pattern): restore consistency with a must-fail probe in the qa-final directive and offer a test-only fix task first; never drop it because the sibling is merged. Found while reviewing an unrelated fix task, it is no Required Action of that task. Found while reviewing the still-open fix task for the same class and file scope and proven by a run, fold it in as a REJECT with a test-only RA if the orchestrator records the criteria extension in plan.md (cheaper than a certain qa-final FAIL plus a fix task).
   **Pass-through inventory.** For each handler list the distinct input values the tests feed each contract field (`code`, `title`, `details`, ids). A field fed one value survives replacement by it, realistic when it is a natural default (empty list, null, the single catalogue entry for that status). An arbitrary literal no spec names is not realistic, but grep the whole spec pack (`docs/spec-pack/specs/`) before calling it arbitrary (a 503 code "from the exception" was named by later specs). Check `code` and `title`, not `details` alone.
   Single test constants (one id, instant, e-mail in every test) let hard-code mutants survive in mappers; no REJECT under this rule, but if the orchestrator binds them as RAs, prevent the late round with an implDirective data rule ("every pass-through field fed two distinct values, asserted as literals"), not a stricter verifier bar.
   A `valueOf(status)` hand-off killed by an unknown value still lets a case-folding or `strip()` variant survive: inspection-proven when the writer stores `name()` and the criterion pins plain `valueOf`.

10. **No red run.** Tests written first with a green first run are no gate finding outside an sdd-bugfix lead directive, provided every criterion clause bites on the gated bytes (a must-fail probe kills it, or I kill it by reading); judge a clause with neither under lenses 3 and 4. When a bugfix's root-cause file is the test itself, check which line each red fixed-bytes probe fails at: if all fail on neighbouring lines, the rewritten assertion has no run evidence. Unlisted in the plan and exact by reading: ENDORSE, brief one qa-final probe per direction (Flyway history: an extra location holding a V file; a `SELECT 1` V file above `spring.flyway.target`, never a target below a schema migration). For "tests never see the seed" in a module log, find the test-profile context as `applied N migrations` with no `with repeatable migration` line before it; `DemoSeedCensusIntegrationTest` opens its own seeded databases, so a raw `now at version` count over-claims contexts.
    Implementer red taken before editing the pages proves the page side only (check files may not be final): accept when the verifier's NC on the final bytes repeats the messages verbatim and explains every extra red.

11. **Implementer edits outside its file scope.** In rework rounds implementers sometimes mutate a production file to prove their fix kills the survivor. If it is restored, the verifier's snapshot and baseline show it hash-identical, runs did not overlap and the gate evidence is the verifier's own, it is a process finding for the orchestrator, not a gate finding. Implementer probe logs are never gate evidence: a verdict leaning on them, or overlapping runs, gets a CHALLENGE. Prevention wording: [[qa-directive-traps]] item 17.

12. **A disclosed probe-restore slip** is no finding when: (a) before and after snapshots are identical; (b) every gated file's mtime is earlier than snap-after and the referee start and its current hash equals snap-before; (c) every probe run after the slip fails at a line the stray form cannot explain, or the stray form is equivalent. If (c) fails for a probe, it has no evidence: CHALLENGE for a re-run. Prevention: [[qa-directive-traps]] item 3.
    An env-selected mutant schema (one schema file per production class, `switch` on an env variable, `default` = original) is valid probe evidence when a control run with the variable unset is green, I have read every `case` against its named mutant, and each probe is its own `clean test` run with its own log, restored by `cp` and hash-checked. Annotation mutants cannot be switched.
    Two sort probes giving the same permutation leave byte-identical failure text, so the log cannot prove which mutant ran. On a pure pass-through asserted with `containsExactly`, accept one run per distinct permutation plus the column-by-column sequence argument (the kill is a function of the stub data, verified by reading).

13. **A rework edit to an asserting line that follows a data edit** is no lens 6 REJECT when: production is hash-identical; the element set and matcher are unchanged (the new expected value is the spec rule recomputed on the new inputs); every probe the old line killed was re-run and is still killed by some test; the edit kills more than before. A lost redundant kill is acceptable when the test named for the criterion still kills it with decorrelated data. **Why:** extra hardening beyond my RA (tie data in a second test) changed the expected order; calling it a loosening would punish a stronger test. **How to apply:** check by reading which mutants only the edited test kills (a level-relative order key) and confirm they still die.

14. **A brief expectation refuted by evidence.** When a verifier shows an expected value in my directive came from a false premise (library behaviour, a count), ENDORSE lowers no bar if: no criterion pins the expected value; the binding property behind it still holds and I confirm it myself (one read-only check such as `javap -c` plus reading the production rule); the verifier backs the refutation with a control (U+00A0 gives 202 where U+2003 gives 400). Then fix the premise in the spec docs at finalize and correct my ledger and memory. If a criterion pins the refuted value, it is a product question for the orchestrator.
    Same family (ENDORSE plus a plan-level decision or amendment recommendation, no bar lowered):
    - A C0 warning-class example ("fixable in scope = FAIL") whose only fix breaks a pinned criterion (a logback status line from a spec-mandated empty pattern): the exact-count acceptance is fine when stdout is tested unfiltered and the count bites both ways; record the line as a product residual.
    - A criterion whose literal wording the orchestrator's own mandated process breaks (plan.md bookkeeping commit vs "no file outside ci.yml on the task branch"): ENDORSE when the protected property (no product file changed) is proven; recommend the wording fix at finalize.
    - A must-fail probe that cannot run as written or is an equivalent mutant (confirm by `javap` plus a witness diff over methods x paths): the verifier's substitute is valid when the original's log shows the other cause (the control) and the substitute breaks only the property under test and fails at the scenario's state assertions. Offer the corrected probe as a plan amendment. If the pin is my own QA rewrite, I rule it myself: ENDORSE plus an amendment with the exact new wording, provided the corrected must-fail probe dies.
    - The opposite case: a fail-closed premise I wrote into an RA ("this over-approximation is safe") that the verifier refutes with builds while a closed grading rule I also wrote FAILs the task. The grading rule governs; reclassing refuted cases as residual narrows the bar after the fact, which only a human override may do. AMEND the RA's acceptance condition if it contradicts its own fix, own the premise in the ledger, give the human options with a structural guard.
    - A harness mandate: the attribution footer's U+1F916 under my "PR body ASCII only" is accepted when the prose is ASCII and no criterion pins the body. A base merged mid-sweep adding a hit to a directory-wide grep is no finding when `git grep` on both bases attributes it and the file is outside the spec diff. A base moving AFTER a qa-final PASS is no CHALLENGE when `git log --stat <old>..<new>` touches no file of `git diff --name-only <old>...<tip>`: ENDORSE and hand the mergeability re-check to the orchestrator (`gh pr view` shows UNKNOWN while GitHub recomputes).
    - A card clause naming an analogue test that does not exist ("behaves like the existing receive test"): ENDORSE when the verifier measured the property with a removed temporary test and the orchestrator ruled the clause; record a residual plus a qa-final item. Prevent: grep every named analogue before it enters a falsifier list.
    - A bugfix NC "fails on exactly the tests of criteria 1 and 2" while sibling criteria test a new element: extra reds are fine if no pre-existing test is red and each fails at its first behavioural assertion; write NC criteria as "named shapes, no pre-existing test red".
    - At a fetch-joined `order by`, an `@OrderColumn` position is a flat child column reachable only as `index(l)`; its `asc` sort ties every root at position 0, so no data forces it: an inspection item next to the removed tiebreak, not a survivor.

15. **Oracle-hardening gaps outside the criteria.** When a verifier finds that a self-written checker passes vacuously in a way no criterion covers (zero self-tests discovered still exits 0), do not REJECT the PASS. Make it a criterion amendment for the next task that owns the same files, with must-fail witnesses. Until then, add a verifier-side guard: the test total is never below the last gated total, and the earlier test titles are a subset of the current ones. "N equals the grep count" misses a deleted test file, because both numbers drop together (spec 11 T1), and is false when loops register cases (spec 14 T1: 602 run, 559 calls); never write it.
   Test-only gaps need a route, not a rework round. An untested extra guard (not in the falsifier list, unreachable in the spec) in a file no later task owns: ENDORSE, route its test to the next task on the same seam by a fileScope line, must-fail there (spec 14 T1 NM25 -> T2). A batch of checker-strictness survivors when the next task does not share the seam: an insertion-only scope amendment for the round that runs anyway, with exact fixtures and a base-file control (spec 14 T2 -> T3, A3). In the LAST task (no round to ride): ENDORSE, owner residual folded into the next spec that reopens the module, a qa-final must-fail per entry on the tip, and verbatim test-only RAs the orchestrator may bind (spec 14 T3 R6).

16. **Regression-guard survivors in a file that freezes at this PASS.** A survivor that narrows a property class (a Unicode property replaced by categories, one element type instead of any) is no REJECT, even on a critical rule, when the verifier proved the current bytes on every member (exhaustive enumeration through the real function plus a real build), the file joins the freeze hash baseline at merge and another gate or authoring grep already rejects the reachable forms. Record a follow-up (exhaustive loop, then re-baseline). Before accepting a "reachable residual", check whether a hygiene gate rejects the probe source (raw non-ASCII fails the ascii rule; only references and escapes reach a label).

17. **Orchestrator-approved deviations on a refuted premise.** When the orchestrator approved a departure from a card bullet for a factual reason a verifier then refutes ("no link to an anchor that does not exist" while the skeleton had it) and every criterion still holds: ENDORSE. Return the decision with the refuted premise and the cheapest restoring path (a later task's one-line fileScope amendment re-bound by "the file with the line removed hashes to the stored value"). Scope is the orchestrator's; declining is an owner residual. Scratch-layer assertions pinning such a decision (not pack text) are re-pointed before qa-final re-runs them.

18. **Survivors killed by a gate grep.** Before judging an "informational survivor", check whether a common-directive gate check rejects the mutant (a clock grep that must print exactly one `Clock.system` line rejects a bean built with `Clock.systemUTC()`; a mapper grep rejects `JsonMapper.builder()` in main). Then it is gate-proven, as long as the grep runs in every later task and qa-final; feed a test-pinned follow-up only if the clause is high-risk under rule 3. Verifiers miss this. Exception: when a criterion says the test asserts criterion N ("the census asserts ... plus criterion 2"), N's gate-grep properties (ASCII only) are test items: fold them in as RAs when a rework round runs anyway.

19. **"Covered one layer down" survivors in an integration-test task.** An IT over endorsed layers often lets a flow mutant survive (an order or hand-off its data never shows). It counts as killed when its body equals a probe in the earlier gate's schema and the rule 1 carry holds (both hashes equal now, result line on disk): diff the mutant against the `.orig`, find the case in the earlier schema, quote its result line. No re-run, no REJECT; a hash change makes it a qa-final re-run item.

20. **A named read-only check the verifier skipped** (a contract hash baseline, an `ls -lT` listing) while a broader check it ran (whole-tree `git status`/`diff --stat`) already shows the property: I run the read-only check myself, record it, no CHALLENGE. CHALLENGE is for a missing check that needs a test run, or evidence that contradicts itself. Diff every reused mutant against its hash-checked `.orig` myself (verifiers sometimes say the generator is missing when it is not).
    Lens 2 ordering: agent frontmatter `updated` can be off by tens of minutes; order by `ls -lT` mtimes plus the verifier's copy-aside hashes.
    Same for a check that sat only in a feed-forward and never reached the task block (repo-wide `-w` count grep): verifiers run the block, not the ledger. Prevention: copy every FF check into the T<n> block it targets.

21. **Boundary twin of a fixed survivor.** When a rework kills survivor X and the verifier reports X's boundary twin (`>` vs `>=`) as "informational", judge the twin under the same criterion as X: same reachable-input test, same verdict. Spend the rework round only on fully specified test-only RAs (state, act, every asserted value, the mutant each must kill) and fold in other cheap in-criterion survivors of the same files.
    For a boolean state flag the twin of a "reset" mutant is the "set" mutant, and each flag value is its own region: an "unchanged" claim needs every test to run from both values (parameterize), not sibling tests starting from one value each.
    The line stops at the twin. An offset shift (`>= level - 1`, `- 2`) inside a region that already has a witness, or a one-sided spelling (`stripLeading` where `strip`/`trim`/`stripTrailing` die), is no criterion failure when production holds no such guard: no last-round REJECT. Route the witness into the next task's own data at the same seam and make the mutant must-fail there. My RA skeleton should sit 2 or more inside the region, not 1, so the `-1` twin dies too.

22. **A verification task that finds a product defect outside its fileScope** (record-and-screenshots task reproducing a layout defect or 404 resource) is ENDORSEd, not REJECTed, when the record discloses it truthfully with evidence, the verifier reproduced it independently and the orchestrator assigned a fix task. State in the meta-verdict that the ENDORSE certifies the verification, not the failing property; the fix task and qa-final close it live, and the fix task refreshes every record line and screenshot it makes stale. **Why:** a REJECT has no meetable RA; silent endorsing would let Gate 2 read the property as proven.
    A qa-final report-only observation (a reload during a held order, Confirm again, two orders) is a Gate 2 residual, not a fix task, when it lies outside every criterion's scope, behaves the same on the base and its real fix needs a product decision (server idempotency key vs persisted in-flight marker with a lost-answer policy): name the decision and options.

23. **Environment-only survivors and bounding the escalated round (bash tooling).** A survivor that differs only when a file descriptor itself fails (stderr closed), under a concurrent writer or a double fault, whose harm lies outside the criterion's protected property (a temp folder leak vs "target tree unchanged"), is struck under AMEND to a follow-up plus a final gate grep, not kept as a last-round RA; the `rm` twin of a killed `cp` restore failure stays (rule 18). **Why:** each round's new code yields a narrower mutant class; without a bound the loop never closes. **How to apply:** the escalated round gets a closed RA list, production hash-pinned, insertion-only tests, a re-run of only the batch whose cases changed, and FAIL grounds limited to unmet RAs, regressions, drift or a defect witness.
    An impl artifact stamped after the verdict is no lens 2 finding when every gated file's mtime predates the verifier's run start and its hash equals the verifier's final hash: judge bytes, not artifact stamps. A trailing space stripped from an "insertion only" evidence file is no finding when `git grep -F` still finds the line as a byte prefix of its source and `.editorconfig` trims trailing whitespace; write such bounds "modulo trailing whitespace".

24. **Classing nits in authored docs and rehearsal rows.** A false statement in the task's own file is a FAIL when it can change what the reader does or concludes (a provenance claim, a code-naming rule, a locale equivalence, a literal the reader compares output with). A clerical pointer that its own citing documents contradict (wrong row number in an evidence header), an incomplete summary list whose omitted item carries its own label at the point of use, or an omitted step whose row keeps a working judge is a correction follow-up, not a late-round REJECT. **Why:** the first class misleads a rehearsal; the second cannot, and a round on it delays parallel tasks. **How to apply:** ask the verifier to class each nit; check the environment the product really uses before accepting an environment nit (Claude Code starts shell-form hooks with `sh -c` on macOS and Linux); require known-false lines fixed by an appended correction, not left for an insertion-only bound.

25. **A live check whose data cannot discriminate.** A final-sweep journey comparing page figures with the API proves nothing about "server figures, not the estimate" when the seeded data makes both equal. ENDORSE when the verifier discloses it and names the unit witness that does discriminate (server total differs from the line sum), which I read. In a final brief ask for that witness by file:line, not a live equality the data cannot break. Never write isolation premises as one named container that may not exist, nor "the full `docker ps -a` listing is identical before and after" (parallel cycles start containers; Status carries uptime). Write: names-only listings before and after, the agent's own container absent after, every diff name quoted as foreign (reported, never touched), the shared container's `State.StartedAt` identical.

26. **"Same wording elsewhere" in a comment-fix task.** Before calling a sibling sentence the same defect, tell a class claim (a code-formatted class named as the rule's holder, false) from a layer claim ("the flow owns it", meaning the flow answers 422), and grep earlier cycles' plans for a criterion that pinned the wording. A pinned, true layer claim is no blast-radius gap: ask for a "checked, consistent" line in bug.md, not a follow-up bug.
    For a pack-wording bug grep all of `docs/spec-pack/` myself (roadmap.md repeated a fixed rule while bug.md grepped guide/ and the plan only); a hit outside the authorised lines is a question to the orchestrator plus a qa-final attribution item, never an RA.
    A final-brief "expected hits / PASS only if" list is built by running that item's exact grep myself and attributing every hit (specs/ states page grammar too); an incomplete list makes a literal qa-final FAIL on a disposition-only gap.

27. **Probabilistic concurrency witnesses.** A latch-and-threads test against a removed `synchronized` is killed in some runs and survives in others with the same bytes. Count all runs across rounds, apply the pre-declared three-run rule literally, and do the inspection myself (shared state private and touched only inside the guarded method). ENDORSE, then pin the guard with a qa-final gate grep (rule 18). Offer an optional deterministic witness: a test `Clock` whose `instant()` records the maximum number of threads inside it while it waits on a latch nobody releases, asserted to be 1. Never spend a rework round on it.

28. **Constant-only production diffs.** A changed `static final` primitive or String literal is a ConstantValue attribute inlined at its use sites: JaCoCo has no probe on that line, so "coverage not measured" is no lens 1 gap. The evidence is one must-fail probe per neighbour value (n-1, n+1, the old value, unbounded) plus the hand-off probes one layer down.

29. **Skipped dev-mode walk (verifier definition 6(b)) on a UI fix.** For a mapping-only change in an existing render path (no new component, hook, list or DOM) whose component test renders the real page under the setupTests console trap: ENDORSE and move the walk to qa-final as a required item (Vite dev, fresh context, `page.route` with the real server body, console dump), not a CHALLENGE. A new component or list is a CHALLENGE. Correct a "not provisionable" reason: `page.route` needs no backend.
