:::note[At a glance]

**Goal:** Turn a vague request into a spec, a plan and tasks, then let the agent implement and verify it inside the harness you built.

**Start branch:** `start/level-4-<track>`

**Catch-up:**

```bash
git stash -u && git switch start/level-4-<track>
```

**Time:** 45 minutes

:::

In this level you pick a track and a feature brief, turn the brief into a spec, a plan and tasks, then let the agent implement and verify it inside the harness you built.

## Tracks {/* #tracks */}

Pick a track and switch to its prepared branch (built from `solution/level-3`, with the framework's project files already in place):

| Track | Branch | Weight | Commands you will use |
|---|---|---|---|
| A: OpenSpec | `start/level-4-openspec` | Light | `/opsx:explore`, `/opsx:propose`, `openspec validate --strict`, `/opsx:update`, `/opsx:apply`, `/opsx:archive` |
| B: Spec Kit | `start/level-4-speckit` | Heavier, most guard rails | `/speckit-specify`, `/speckit-clarify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement`, `/speckit-converge` |
| C: Agent OS | `start/level-4-agentos` | Light, standards-centric | `/plan` then `/shape-spec`, `/inject-standards`, implement the plan |

Common start for every track:

```bash
git stash -u                         # keep your own Level 3 work if you like
git switch start/level-4-<track>     # openspec | speckit | agentos
claude                               # new session; /model sonnet
```

The start branches are built from `solution/level-3`: your Level 2 and Level 3 harness (`.mcp.json`, the `jdtls-lsp` plugin declaration, hooks, permissions, skill, `/ship`) plus the framework's project files, already in place (each tab below says what its branch holds). Pick a feature brief from the [feature briefs](#feature-briefs) below. Write the brief into the first command in your own words and add the answers to its questions: that is your contribution as the human.

The steps below use the example names of brief A (`add-book-reviews`, `add book reviews`). With brief B or C, use your own change name.

A track takes about 35 minutes; the rest of the 42 solo minutes is for choosing a track and a brief at the start and for the final checks at the end.

Open the tab of your track.

  <TabItem value="openspec" label="Track A: OpenSpec">

About 35 minutes.

The start branch holds an initialised OpenSpec project: `openspec/config.yaml` and one spec in `openspec/specs/ordering/spec.md`, plus the `/opsx` commands in `.claude/commands/opsx/`. It does not hold the `openspec` program. If `openspec --version` does not print 1.16.0 yet, install that version:

  <TabItem value="unix" label="macOS/Linux">

```bash
curl -fsSL https://openspec.dev/cli/install.sh | OPENSPEC_VERSION=v1.16.0 sh
```

  </TabItem>
  <TabItem value="windows" label="Windows PowerShell">

```powershell
$env:OPENSPEC_VERSION = "v1.16.0"
irm https://openspec.dev/cli/install.ps1 | iex
```

  </TabItem>
</Tabs>

With Node.js 22.12 or later, npm installs the same version instead:

```bash
npm install -g @fission-ai/openspec@1.16.0
```

Check it:

```bash
openspec --version
```

1. Run the command below with "reviews and ratings" (or your brief) after it: the agent reads the code you are about to change.

   ```text
   /opsx:explore
   ```

2. Propose the change with your brief and decisions:

   ```text
   /opsx:propose add-book-reviews
   ```

3. In your terminal, validate it. Fix what it reports. Common error: a scenario heading with three `#` instead of four is silently ignored.

   ```bash
   openspec validate add-book-reviews --strict
   ```

4. Read `openspec/changes/add-book-reviews/specs/.../spec.md`. Change what is wrong with this command:

   ```text
   /opsx:update
   ```

5. Clear the context first:

   ```text
   /clear
   ```

   Then apply the change and watch the tasks tick off:

   ```text
   /opsx:apply
   ```

6. Commit through your `/ship` command. The test-gate hook runs.

   ```text
   /ship add book reviews
   ```

7. Archive the change. Your requirements are now part of the living spec in `openspec/specs/`.

   ```text
   /opsx:archive
   ```

Gotchas: `openspec ...` runs in the terminal, `/opsx:...` in Claude Code. If the commands do not show up, restart Claude Code.

**For your own brownfield project**, the first steps from the [OpenSpec docs](https://github.com/Fission-AI/OpenSpec/blob/v1.16.0/docs/existing-projects.md), once the program is installed:

1. `openspec init` in your repository.
2. Optionally fill in `context:` in `openspec/config.yaml` with your stack and conventions.
3. Then the same flow as in this track: `/opsx:explore`, `/opsx:propose`, `/opsx:apply` and `/opsx:archive`.

   ```text
   /speckit-plan
   ```

4. Create the tasks:

   ```text
   /speckit-tasks
   ```

5. Implement, then converge once:

   ```text
   /speckit-implement
   ```

   ```text
   /speckit-converge
   ```

6. Commit through your `/ship` command:

   ```text
   /ship add book reviews
   ```

Skip `/speckit-checklist` and `/speckit-analyze` today; try them at home.

Gotchas: in Claude Code the commands are `/speckit-specify` (dash), the dotted names are documentation notation. The active feature is stored in `.specify/feature.json`, not taken from the git branch.

**For your own brownfield project**, the first steps from the [Spec Kit docs](https://github.com/github/spec-kit/blob/v1.3.1/docs/how-to/existing-projects.md), after installing it as on the [wrap-up page](./06-wrap-up.md#install-a-spec-framework-yourself):

1. `specify init --here --force --integration claude` in your repository.
2. `/speckit-constitution` with the rules your project already follows.
3. Then `/speckit-specify` for one small change, followed by `/speckit-clarify`, `/speckit-plan`, `/speckit-tasks` and `/speckit-implement`.

  <TabItem value="agentos" label="Track C: Agent OS">

About 35 minutes.

The start branch holds Agent OS product docs in `agent-os/product/` and standards written for this repo and indexed in `agent-os/standards/index.yml`, plus the commands in `.claude/commands/agent-os/`.

1. Look at `agent-os/standards/` first: they were written for this repo and indexed. Fix anything wrong.

2. Enter plan mode (or press `Shift+Tab` until plan mode):

   ```text
   /plan
   ```

   Then shape the spec with your brief and decisions:

   ```text
   /shape-spec
   ```

3. Answer its questions; let it save the spec folder in `agent-os/specs/`.

4. Approve the plan and let Claude implement it. Use this command if tests drift from the conventions:

   ```text
   /inject-standards testing
   ```

5. Commit through your `/ship` command:

   ```text
   /ship add book reviews
   ```

Gotchas: `/shape-spec` refuses to run outside plan mode. Agent OS needs bash: on Windows use WSL or Git Bash.

**For your own brownfield project**, the first steps from the [Agent OS docs](https://buildermethods.com/agent-os/workflow), after installing it as on the [wrap-up page](./06-wrap-up.md#install-a-spec-framework-yourself):

1. `/discover-standards` to extract the patterns your code already follows.
2. `/inject-standards` before you implement.
3. `/plan-product` for the mission and the roadmap.
4. `/shape-spec` in plan mode, for each change.

:::tip[Make it yours]

Spec-driven does not mean someone else's rules. Invent one of your own that every future spec must follow, and see whether the agent keeps to it: a rule in `openspec/config.yaml`, a principle in `.specify/memory/constitution.md` or a standard in `agent-os/standards/`. The best harness has a creative engineer tweaking it all the time.

:::

## Feature briefs {/* #feature-briefs */}

Pick one. Each brief is written the way a product owner would ask for it: incomplete on purpose. Turning it into a precise, testable spec is the point of the level.

A fits every track in 35 minutes. B is fine for OpenSpec and Agent OS, tight for Spec Kit. C is for people who finished early or know Spring AI.

### Brief A: Reviews and ratings (recommended for most people)

> "Customers keep asking which books are actually good. Let them leave a rating from 1 to 5 stars and a short review for books they bought. Show the average rating in the catalogue search."

Questions your spec should answer: who may review (only customers with a shipped order containing the book?), one review per customer per book or edits allowed, review length, how the average is rounded and shown when there are no reviews, whether discontinued books keep their reviews.

### Brief B: Wishlist with back-in-stock notice

> "When a book is out of stock, customers should be able to put it on a wishlist, and we tell them when it is back."

Questions your spec should answer: identify customers by e-mail like orders do?, what "tell them" means here (no real e-mail: record a `NotificationRequested` entry that a query can list), what happens when stock comes back while a restock is pending, limits per customer. Touches the `process` layer: a new domain event when stock becomes available again.

### Brief C: Assistant recommends from the distributor (advanced)

> "When we don't have what a customer asks for, the assistant should suggest titles from our distributor that we could order for them."

Questions your spec should answer: how the assistant reaches the distributor, how suggestions are clearly marked as "not in stock, can be ordered", what the assistant must never promise (delivery dates?), how tests stay offline.

Two routes, and your spec must pick one explicitly:

1. **Within the architecture (recommended):** add a `searchTitles` method to the `DistributorAppService` port, implement it over REST in `acl`, expose it to the model through a new tool that calls a flow. Tests: scripted chat model plus a mocked port.
2. **Via MCP:** use Spring AI's MCP client against our distributor MCP server. This breaks two rules on purpose (outbound integration only through `acl`; `CLAUDE.md` says the distributor is reached only through the port), so your spec must include an architecture change: update `docs/architecture.md`, `CLAUDE.md` and the ArchUnit rule with a documented exception. That is a legitimate outcome of a spec, as long as it is explicit.

Whichever brief you pick, once your spec artefact is committed, ask someone on another track to show theirs: an OpenSpec delta spec, a Spec Kit spec.md and an Agent OS shape.md hold the same idea in three shapes.

## Level cleared when

- [ ] Spec artefacts committed next to the code.
- [ ] `./mvnw verify` green, including `ArchitectureTest`, shown in the terminal (not claimed).
- [ ] Commit made through your `/ship` command and passed the test-gate hook.
- [ ] Every acceptance scenario in your spec maps to a test (ask the agent to list the mapping).
