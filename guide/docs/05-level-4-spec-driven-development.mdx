**Goal:** Turn a vague request into a spec, a plan and tasks, then let the agent implement and verify it inside the harness you built.

**Start branch:** `start/level-4-<track>`

**Catch-up:**


In this level you pick a track and a feature brief, turn the brief into a spec, a plan and tasks, then let the agent implement and verify it inside the harness you built.

## Tracks {/* #tracks */}

Pick a track and switch to its prepared branch (built from `solution/level-3`, framework installed, project conventions captured):

| Track | Branch | Weight | Commands you will use |
|---|---|---|---|
| A: OpenSpec | `start/level-4-openspec` | Light | `/opsx:explore`, `/opsx:propose`, `openspec validate --strict`, `/opsx:update`, `/opsx:apply`, `/opsx:archive` |
| B: Spec Kit | `start/level-4-speckit` | Heavier, most guard rails | `/speckit-specify`, `/speckit-clarify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement`, `/speckit-converge` |
| C: Agent OS | `start/level-4-agentos` | Light, standards-centric | `/plan` then `/shape-spec`, `/inject-standards`, implement the plan |

Common start for every track:

```bash
git stash -u                         # keep your own Level 3 work if you like
git switch start/level-4-<track>     # openspec | speckit | agentos
claude                               # new session; /model sonnet
```

The start branches are built from `solution/level-3`: your Level 2 and Level 3 harness (`.mcp.json`, the `jdtls-lsp` plugin declaration, hooks, permissions, skill, `/ship`) plus the framework, already installed and configured. Pick a feature brief from the [feature briefs](#feature-briefs) below. Write the brief into the first command in your own words and add the answers to its questions: that is your contribution as the human.

The steps below use the example names of brief A (`add-book-reviews`, `add book reviews`). With brief B or C, use your own change name.

Open the tab of your track.

  <TabItem value="openspec" label="Track A: OpenSpec">

About 35 minutes.

1. Run the command below with "reviews and ratings" (or your brief) after it: the agent reads the code you are about to change.

   ```text
   /opsx:explore
   ```

2. Propose the change with your brief and decisions:

   ```text
   /opsx:propose add-book-reviews
   ```

3. In your terminal, validate it. Fix what it reports. Common error: a scenario heading with three `#` instead of four is silently ignored.

   ```bash
   openspec validate add-book-reviews --strict
   ```

4. Read `openspec/changes/add-book-reviews/specs/.../spec.md`. Change what is wrong with this command:

   ```text
   /opsx:update
   ```

5. Clear the context first:

   ```text
   /clear
   ```

   Then apply the change and watch the tasks tick off:

   ```text
   /opsx:apply
   ```

6. Commit through your `/ship` command. The test-gate hook runs.

   ```text
   /ship add book reviews
   ```

7. Archive the change. Your requirements are now part of the living spec in `openspec/specs/`.

   ```text
   /opsx:archive
   ```

Gotchas: `openspec ...` runs in the terminal, `/opsx:...` in Claude Code. If the commands do not show up, restart Claude Code.

## Feature briefs {/* #feature-briefs */}

Pick one. Each brief is written the way a product owner would ask for it: incomplete on purpose. Turning it into a precise, testable spec is the point of the level.

A fits every track in 35 minutes. B is fine for OpenSpec and Agent OS, tight for Spec Kit. C is for people who finished early or know Spring AI.

### Brief A: Reviews and ratings (recommended for most people)

> "Customers keep asking which books are actually good. Let them leave a rating from 1 to 5 stars and a short review for books they bought. Show the average rating in the catalogue search."

Questions your spec should answer: who may review (only customers with a shipped order containing the book?), one review per customer per book or edits allowed, review length, how the average is rounded and shown when there are no reviews, whether discontinued books keep their reviews.

### Brief B: Wishlist with back-in-stock notice

> "When a book is out of stock, customers should be able to put it on a wishlist, and we tell them when it is back."

Questions your spec should answer: identify customers by e-mail like orders do?, what "tell them" means here (no real e-mail: record a `NotificationRequested` entry that a query can list), what happens when stock comes back while a restock is pending, limits per customer. Touches the `process` layer: a new domain event when stock becomes available again.

### Brief C: Assistant recommends from the distributor (advanced)

> "When we don't have what a customer asks for, the assistant should suggest titles from our distributor that we could order for them."

Questions your spec should answer: how the assistant reaches the distributor, how suggestions are clearly marked as "not in stock, can be ordered", what the assistant must never promise (delivery dates?), how tests stay offline.

Two routes, and your spec must pick one explicitly:

1. **Within the architecture (recommended):** add a `searchTitles` method to the `DistributorAppService` port, implement it over REST in `acl`, expose it to the model through a new tool that calls a flow. Tests: scripted chat model plus a mocked port.
2. **Via MCP:** use Spring AI's MCP client against our distributor MCP server. This breaks two rules on purpose (outbound integration only through `acl`; `CLAUDE.md` says the distributor is reached only through the port), so your spec must include an architecture change: update `docs/architecture.md`, `CLAUDE.md` and the ArchUnit rule with a documented exception. That is a legitimate outcome of a spec, as long as it is explicit.

Once your spec artefact is committed, ask someone on another track to show theirs: an OpenSpec delta spec, a Spec Kit spec.md and an Agent OS shape.md hold the same idea in three shapes.

## Level cleared when

- [ ] Spec artefacts committed next to the code.
- [ ] `./mvnw verify` green, including `ArchitectureTest`, shown in the terminal (not claimed).
- [ ] Commit made through your `/ship` command and passed the test-gate hook.
- [ ] Every acceptance scenario in your spec maps to a test (ask the agent to list the mapping).
